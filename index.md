# Урок 9. Классы, инварианты и композиция

## 1. Первый класс

Мне кажется, здесь стоит с самого начала обозначить рамки урока: **мы изучаем не ООП, а то, как TypeScript работает с классами**. 

Сегодня мы начинаем изучать классы в TypeScript.

Важно сразу отметить один момент.

Классы появились не в TypeScript. Они существуют в самом JavaScript.

TypeScript не изобретает новую модель классов, а добавляет к ней типизацию и дополнительные возможности, которые помогают писать более безопасный и понятный код.

Поэтому в этом уроке мы будем говорить именно о возможностях TypeScript, а не изучать объектно-ориентированное программирование целиком.

---

Начнем с самого простого класса.

```ts
class BankAccount {
  owner: string;
  balance: number;

  constructor(owner: string, initialBalance: number) {
    this.owner = owner;
    this.balance = initialBalance;
  }

  deposit(amount: number): void {
    this.balance += amount;
  }
}

const account = new BankAccount("Анна", 1000);

account.deposit(500);

console.log(account.balance);
```

Разберем этот код по частям.

Сначала объявляется класс.

```ts
class BankAccount
```

После имени класса находятся его свойства.

```ts
owner: string;
balance: number;
```

Обратите внимание на главное отличие от JavaScript.

Мы сразу указываем типы свойств.

TypeScript знает, что **owner** — это строка, а **balance** — число.

Благодаря этому компилятор сможет обнаружить ошибки еще до запуска программы.

---

Далее идет конструктор.

```ts
constructor(owner: string, initialBalance: number)
```

Он вызывается автоматически при создании нового объекта.

Типы параметров тоже указываются явно.

Внутри конструктора значения сохраняются в свойства объекта.

```ts
this.owner = owner;
this.balance = initialBalance;
```

Ключевое слово **this** обозначает текущий экземпляр класса.

---

Теперь посмотрим на метод.

```ts
deposit(amount: number): void {
  this.balance += amount;
}
```

У метода есть типизированный параметр

```ts
amount: number
```

и явно указан тип возвращаемого значения.

```ts
void
```

Это означает, что метод ничего не возвращает.

---

После объявления класса можно создать его экземпляр.

```ts
const account = new BankAccount("Анна", 1000);
```

Оператор **new** вызывает конструктор и создает новый объект.

После этого можно обращаться к его методам.

```ts
account.deposit(500);
```

И к его свойствам.

```ts
console.log(account.balance);
```

На экран будет выведено

```text
1500
```

---

На первый взгляд все выглядит вполне корректно.

Но здесь уже есть одна проблема.

Поле

```ts
balance
```

остается полностью открытым.

Поэтому внешний код может написать, например,

```ts
account.balance = -1000;
```

TypeScript не сообщит об ошибке.

С точки зрения типов здесь все правильно: **balance** действительно имеет тип **number**.

Но с точки зрения логики приложения отрицательный баланс может быть недопустимым.

Получается интересный вывод.

**Типизация отвечает только за корректность типов данных.**

Она не знает бизнес-правил вашего приложения.

Именно поэтому одного указания типов недостаточно.

В следующем вопросе мы познакомимся с возможностями TypeScript, которые позволяют ограничить доступ к данным класса и лучше защищать его внутреннее состояние.

## 2. Модификаторы доступа

Вот этот раздел я бы уже полностью сместил в сторону **TypeScript**. Главная мысль должна быть не "что такое инкапсуляция", а **какие модификаторы добавляет TypeScript и как они работают**.

---

## Сценарий урока

В предыдущем примере мы увидели, что одного указания типов недостаточно.

Поле **balance** имело тип **number**, поэтому TypeScript спокойно позволял выполнить такой код.

```ts
account.balance = -1000;
```

Тип данных не нарушен.

Но нарушено правило нашей программы.

Чтобы лучше управлять доступом к данным класса, TypeScript поддерживает модификаторы доступа.

Рассмотрим обновленную версию класса.

```ts
class SafeBankAccount {
  readonly id: string;
  public owner: string;
  private balance: number;

  constructor(
    id: string,
    owner: string,
    initialBalance: number,
  ) {
    if (initialBalance < 0) {
      throw new Error("Начальный баланс не может быть отрицательным");
    }

    this.id = id;
    this.owner = owner;
    this.balance = initialBalance;
  }

  getBalance(): number {
    return this.balance;
  }

  deposit(amount: number): void {
    if (amount <= 0) {
      throw new Error("Сумма пополнения должна быть положительной");
    }

    this.balance += amount;
  }

  withdraw(amount: number): void {
    if (amount <= 0) {
      throw new Error("Сумма списания должна быть положительной");
    }

    if (amount > this.balance) {
      throw new Error("Недостаточно средств");
    }

    this.balance -= amount;
  }
}
```

Разберем новые ключевые слова.

---

Первое свойство выглядит так.

```ts
readonly id: string;
```

Модификатор **readonly** означает, что значение можно установить только один раз.

В данном случае это происходит внутри конструктора.

```ts
this.id = id;
```

После создания объекта изменить идентификатор уже нельзя.

Например,

```ts
const account = new SafeBankAccount("1", "Анна", 1000);

account.id = "2";
```

TypeScript сразу покажет ошибку.

Такой модификатор удобно использовать для идентификаторов, дат создания и других значений, которые не должны изменяться после создания объекта.

---

Следующее свойство.

```ts
public owner: string;
```

Модификатор **public** означает, что свойство доступно откуда угодно.

Например,

```ts
account.owner = "Мария";
```

Такой код совершенно корректен.

Интересно, что **public** можно вообще не писать.

В TypeScript это уровень доступа по умолчанию.

Поэтому следующие записи полностью эквивалентны.

```ts
owner: string;
```

и

```ts
public owner: string;
```

---

Теперь посмотрим на поле баланса.

```ts
private balance: number;
```

Модификатор **private** запрещает обращаться к этому свойству через тип класса.

Например,

такой код уже не скомпилируется.

```ts
account.balance
```

или

```ts
account.balance = 5000;
```

При этом внутри самого класса никаких ограничений нет.

Поэтому методы

```ts
deposit()
```

и

```ts
withdraw()
```

спокойно используют поле

```ts
this.balance
```

Получается, что внешний код больше не может напрямую изменять баланс.

---

Если же нужно узнать текущий баланс,

используется специальный метод.

```ts
getBalance(): number {
  return this.balance;
}
```

Теперь значение можно прочитать,

но нельзя изменить напрямую.

---

Здесь есть одна особенность, о которой важно знать.

Модификатор

```ts
private
```

существует именно в TypeScript.

Он проверяется компилятором.

Поэтому часто говорят, что это **compile-time ограничение**.

После компиляции специального механизма защиты в JavaScript не остается.

---

Но современный JavaScript поддерживает настоящие приватные поля.

Для этого используется символ **#**.

Например,

```ts
class SecretBox {
  #secret: string;

  constructor(secret: string) {
    this.#secret = secret;
  }

  reveal(): string {
    return this.#secret;
  }
}
```

Теперь поле объявляется так.

```ts
#secret: string;
```

Это уже не особенность TypeScript.

Это синтаксис самого JavaScript.

Попытка обратиться к такому полю извне

```ts
box.#secret;
```

приведет к ошибке еще на этапе разбора JavaScript-кода.

---

Возникает вопрос.

Что использовать в реальных проектах?

Если вам достаточно ограничения на уровне TypeScript,

обычно используют

```ts
private
```

Он хорошо интегрируется с системой типов и привычен большинству разработчиков.

Если же требуется настоящее сокрытие данных на уровне JavaScript,

используют приватные поля с символом **#**.

---

Итак, в этом разделе мы познакомились с тремя модификаторами TypeScript.

* **public** — свойство доступно везде. Это значение по умолчанию.
* **private** — свойство доступно только внутри класса.
* **readonly** — значение можно установить при создании объекта, но нельзя изменить позже.

А если необходимо настоящее скрытое поле, которое невозможно прочитать извне даже в JavaScript, используется синтаксис **#private**.

## 3. Parameter properties

Этот раздел уже почти полностью посвящен TypeScript, поэтому его можно сделать более прикладным: показать, **что это за синтаксис**, **что именно генерирует TypeScript** и **когда его стоит использовать**.

---

## Сценарий урока

В предыдущем примере мы сначала объявляли свойства класса.

```ts id="jv5m8q"
readonly id: string;
public owner: string;
private balance: number;
```

А затем в конструкторе снова присваивали им значения.

```ts id="2v0l4e"
this.id = id;
this.owner = owner;
this.balance = initialBalance;
```

Такой код абсолютно нормальный.

Но TypeScript позволяет записать его короче.

Для этого существуют **parameter properties**.

Рассмотрим пример.

```ts id="xj9r6k"
class Product {
  constructor(
    public readonly id: number,
    public title: string,
    private price: number,
  ) {
    if (price < 0) {
      throw new Error("Цена не может быть отрицательной");
    }
  }

  getPrice(): number {
    return this.price;
  }
}
```

На первый взгляд кажется,

что свойства класса вообще исчезли.

Но на самом деле TypeScript создает их автоматически.

---

Посмотрим на первый параметр конструктора.

```ts id="c5t3fn"
public readonly id: number
```

Если перед параметром стоит модификатор доступа,

TypeScript воспринимает его не просто как параметр конструктора.

Он автоматически создает свойство класса

и сразу присваивает ему значение аргумента.

То есть эта запись эквивалентна следующему коду.

```ts id="u3k8rx"
readonly id: number;

constructor(id: number) {
  this.id = id;
}
```

---

То же самое происходит и с полем

```ts id="d7h2kb"
public title: string
```

TypeScript автоматически создаст свойство

```ts id="a8m4zy"
title: string;
```

и выполнит присваивание

```ts id="7q1bce"
this.title = title;
```

---

Аналогично работает и приватное поле.

```ts id="9w4lmt"
private price: number
```

Будет автоматически создано свойство класса

```ts id="5z8npa"
private price: number;
```

и выполнено присваивание

```ts id="ef0q7h"
this.price = price;
```

Получается, что несколько строк кода заменяются одной.

---

Обратите внимание,

что внутри конструктора параметр **price** по-прежнему остается обычной переменной.

Поэтому мы можем выполнять проверки до завершения конструктора.

```ts id="m4x8rl"
if (price < 0) {
  throw new Error("Цена не может быть отрицательной");
}
```

Если значение некорректно,

объект вообще не будет создан.

---

Снаружи класс работает так же, как и раньше.

Можно обратиться к публичным свойствам.

Например,

```ts id="h2n7sw"
const product = new Product(1, "Клавиатура", 7500);

console.log(product.id);
console.log(product.title);
```

А вот получить значение приватного поля напрямую уже нельзя.

```ts id="v9k3fd"
product.price;
```

TypeScript сообщит об ошибке,

поэтому для чтения используется специальный метод.

```ts id="k8f2xu"
product.getPrice();
```

---

Стоит ли всегда использовать такой сокращенный синтаксис?

Не обязательно.

Если у класса два или три простых свойства,

**parameter properties** делают код компактнее и избавляют от повторений.

Но если конструктор начинает выглядеть примерно так,

```ts id="z4n1pc"
constructor(
  public readonly id: number,
  public title: string,
  public category: string,
  public description: string,
  private price: number,
  private discount: number,
  private stock: number,
)
```

читать его становится заметно сложнее.

В такой ситуации часто лучше явно объявить свойства класса

или передавать в конструктор один объект с параметрами.

---

Можно сформулировать простое практическое правило.

**Parameter properties** — это удобное сокращение синтаксиса, которое предоставляет именно TypeScript.

Используйте его, когда оно действительно делает код короче и понятнее.

Если же сокращенная запись ухудшает читаемость класса, лучше выбрать более явный вариант.

## 4. Getter и setter

Этот раздел тоже лучше сделать с акцентом на **возможности TypeScript**, а не на принципы ООП. Здесь главное показать, что TypeScript умеет типизировать `get` и `set`, а также объяснить, когда их удобно использовать.

---

## Сценарий урока

До этого момента мы получали данные с помощью обычных методов.

Например,

```ts id="8r7m2a"
getBalance(): number {
  return this.balance;
}
```

Такой подход совершенно нормален.

Но JavaScript, а вместе с ним и TypeScript, поддерживают еще один механизм — **getter** и **setter**.

Они позволяют обращаться к методам так, словно это обычные свойства объекта.

Посмотрим на пример.

```ts id="g4x9kd"
class Temperature {
  constructor(private celsius: number) {}

  get fahrenheit(): number {
    return this.celsius * 1.8 + 32;
  }

  set fahrenheit(value: number) {
    this.celsius = (value - 32) / 1.8;
  }
}

const temperature = new Temperature(20);

console.log(temperature.fahrenheit);

temperature.fahrenheit = 68;
```

---

Начнем с **getter**.

Он объявляется с помощью ключевого слова

```ts id="u6n3fy"
get
```

В нашем примере он выглядит так.

```ts id="v0q8jc"
get fahrenheit(): number {
  return this.celsius * 1.8 + 32;
}
```

Обратите внимание,

у getter нет параметров.

Он просто вычисляет значение и возвращает его.

TypeScript позволяет указать тип возвращаемого значения точно так же, как и для обычного метода.

В данном случае это

```ts id="4y2phm"
number
```

---

Теперь посмотрим, как используется getter.

```ts id="r3m8ta"
console.log(temperature.fahrenheit);
```

Здесь нет круглых скобок.

Хотя фактически вызывается метод.

Для внешнего кода это выглядит как чтение обычного свойства.

Именно поэтому getter часто используют для вычисляемых значений.

---

Теперь рассмотрим **setter**.

Он объявляется с помощью ключевого слова

```ts id="e8b4kw"
set
```

В нашем примере он выглядит так.

```ts id="6f0nrz"
set fahrenheit(value: number) {
  this.celsius = (value - 32) / 1.8;
}
```

Setter всегда принимает один параметр.

TypeScript позволяет явно указать его тип.

В нашем случае это

```ts id="a9j5vx"
value: number
```

Когда выполняется присваивание,

```ts id="h2p7wd"
temperature.fahrenheit = 68;
```

автоматически вызывается setter.

Он получает значение,

переводит температуру в градусы Цельсия

и сохраняет результат во внутреннем поле класса.

---

Интересно,

что снаружи объекта вообще нет свойства

```ts id="t5v8mc"
fahrenheit
```

Оно вычисляется каждый раз при чтении

и обновляет внутреннее состояние при записи.

Для пользователя класса это выглядит как обычное свойство,

хотя на самом деле работают два разных метода.

---

Стоит ли всегда использовать getter и setter?

Не обязательно.

Они отлично подходят,

когда нужно предоставить удобный доступ к вычисляемым значениям,

как в нашем примере с переводом температуры.

Или когда требуется выполнить небольшую проверку перед сохранением значения.

---

Но если операция представляет собой отдельное действие,

лучше использовать обычный метод.

Например,

для банковского счета гораздо понятнее написать

```ts id="9g4rhk"
account.withdraw(1000);
```

чем пытаться скрыть списание денег внутри setter.

Название метода сразу объясняет,

что происходит,

а код становится проще читать.

---

Поэтому можно запомнить простое правило.

Getter и setter удобно использовать для работы со свойствами и вычисляемыми значениями,

когда объект должен выглядеть как обычная структура данных.

Если же выполняется отдельная бизнес-операция,

например перевод денег, оформление заказа или изменение статуса,

лучше использовать обычный метод с понятным названием.

---

Обратите внимание,

что **getter** и **setter** — это возможности JavaScript.

TypeScript не меняет принцип их работы,

а лишь добавляет к ним статическую типизацию,

позволяя указывать типы параметров и возвращаемых значений и проверять их еще на этапе компиляции.

## 5. Статические члены

Этот раздел тоже можно сделать более "TypeScript-ориентированным". Здесь важно показать, что `static` существует в JavaScript, а TypeScript добавляет типизацию и позволяет комбинировать его с `private constructor`. При этом не уходить в долгие рассуждения про фабрики и DDD.

---

## Сценарий урока

До этого момента все свойства и методы принадлежали конкретному объекту.

Например,

если создать два экземпляра класса,

```ts id="g8n2pw"
const account1 = new BankAccount(...);
const account2 = new BankAccount(...);
```

то каждый объект будет иметь собственные свойства и собственное состояние.

Но иногда данные или методы должны принадлежать не объекту, а самому классу.

Для этого используются **статические члены**.

Рассмотрим пример.

```ts id="v4y8hm"
class OrderNumber {
  private static nextValue = 1;

  static create(): string {
    const number = `ORD-${this.nextValue}`;
    this.nextValue += 1;
    return number;
  }
}

console.log(OrderNumber.create());
console.log(OrderNumber.create());
```

---

Начнем со статического поля.

```ts id="z7k3bd"
private static nextValue = 1;
```

Ключевое слово

```ts id="b9p4qn"
static
```

означает,

что поле принадлежит самому классу,

а не его экземплярам.

Такое поле существует в единственном экземпляре независимо от того, сколько объектов будет создано.

---

Теперь посмотрим на метод.

```ts id="r5m1xf"
static create(): string
```

Это тоже статический член.

Обратите внимание,

метод вызывается не у объекта,

а непосредственно у класса.

```ts id="m8t2ac"
OrderNumber.create();
```

Создавать экземпляр класса для этого не нужно.

Именно поэтому следующий код работать не будет.

```ts id="h6w9vy"
const order = new OrderNumber();

order.create();
```

TypeScript сообщит об ошибке,

потому что статические методы принадлежат классу, а не его экземплярам.

---

Посмотрим,

что делает метод.

Сначала создается номер заказа.

```ts id="d2n7ju"
const number = `ORD-${this.nextValue}`;
```

Затем счетчик увеличивается.

```ts id="x5r8ke"
this.nextValue += 1;
```

Поэтому первый вызов вернет

```text id="q1v4mz"
ORD-1
```

а второй —

```text id="c8k6ra"
ORD-2
```

---

Конечно,

такой счетчик нельзя использовать в настоящей распределенной системе.

Если приложение работает сразу на нескольких серверах,

каждый из них будет хранить собственное значение счетчика.

В этом примере нас интересует только то,

как работают статические поля и методы.

---

Теперь рассмотрим еще один распространенный прием.

```ts id="t9y5gf"
class Email {
  private constructor(public readonly value: string) {}

  static create(value: string): Email {
    const normalized = value.trim().toLowerCase();

    if (!normalized.includes("@")) {
      throw new Error("Некорректный email");
    }

    return new Email(normalized);
  }
}
```

---

Обратите внимание на конструктор.

```ts id="f4w2cp"
private constructor(...)
```

Мы уже знакомы с модификатором

```ts id="n7m3jq"
private
```

Но раньше он применялся к свойствам.

Теперь он используется для конструктора.

Это означает,

что создать объект обычным способом больше нельзя.

Например,

такой код не скомпилируется.

```ts id="y6r8hv"
new Email("User@example.com");
```

---

Возникает вопрос.

Как тогда создать объект?

Для этого используется статический метод.

```ts id="p2k9dt"
Email.create(...)
```

Он становится единственной точкой создания экземпляров класса.

---

Посмотрим,

что происходит внутри метода.

Сначала строка приводится к единому виду.

```ts id="w5c7na"
const normalized = value.trim().toLowerCase();
```

Затем выполняется простая проверка.

```ts id="r8x1mu"
if (!normalized.includes("@")) {
  throw new Error("Некорректный email");
}
```

И только после успешной проверки создается объект.

```ts id="u3f6lb"
return new Email(normalized);
```

Таким образом,

все экземпляры класса проходят одинаковую обработку и проверку данных.

---

Такой подход часто используют,

когда объект нельзя создавать без предварительной проверки или преобразования данных.

В нашем примере невозможно случайно создать объект

```ts id="k7n2qe"
Email
```

с некорректой строкой,

обойдя метод проверки.

---

Итак,

в этом разделе мы познакомились еще с одной возможностью классов.

**Статические поля и методы принадлежат самому классу, а не его экземплярам.**

Их вызывают через имя класса,

не создавая объект.

Кроме того,

статические методы можно использовать как единственную точку создания экземпляров,

например в сочетании с

```ts id="a4m8zs"
private constructor
```

когда необходимо выполнять обязательную проверку или преобразование данных перед созданием объекта.

## 6. Наследование

Этот раздел я бы вообще сделал не про наследование как концепцию ООП, а про **три возможности TypeScript**: `abstract`, `protected` и `override`. Тогда урок останется именно уроком по TypeScript.

---

## Сценарий урока

Само наследование появилось еще в JavaScript.

TypeScript не меняет механизм наследования,

но добавляет несколько полезных возможностей, которые делают код более безопасным и понятным.

Рассмотрим пример.

```ts id="w7r3mq"
abstract class PaymentProcessor {
  constructor(protected readonly merchantId: string) {}

  abstract pay(amount: number): Promise<string>;

  protected validateAmount(amount: number): void {
    if (amount <= 0) {
      throw new Error("Сумма должна быть положительной");
    }
  }
}

class CardPaymentProcessor extends PaymentProcessor {
  override async pay(amount: number): Promise<string> {
    this.validateAmount(amount);
    return `card-${this.merchantId}-${Date.now()}`;
  }
}
```

---

Первое новое ключевое слово —

```ts id="m9k2pc"
abstract
```

Оно используется при объявлении класса.

```ts id="j4t8va"
abstract class PaymentProcessor
```

Абстрактный класс нельзя создать напрямую.

Например,

```ts id="f2w6zn"
new PaymentProcessor("shop-1");
```

TypeScript сразу покажет ошибку.

Такой класс существует только как основа для других классов.

---

Внутри класса находится еще одно ключевое слово.

```ts id="r8x1lm"
abstract pay(amount: number): Promise<string>;
```

Это абстрактный метод.

У него нет реализации.

Он только задает контракт,

который обязаны реализовать все наследники.

Если какой-либо наследник не определит собственный метод

```ts id="q5n7dy"
pay()
```

TypeScript сообщит об ошибке компиляции.

---

Теперь обратим внимание на конструктор.

```ts id="a3v8kp"
constructor(
  protected readonly merchantId: string
)
```

С модификатором

```ts id="k1m4tu"
readonly
```

мы уже знакомы.

После создания объекта идентификатор магазина изменить нельзя.

---

Новым здесь является модификатор

```ts id="x7p9rb"
protected
```

Он похож на

```ts id="d5n2wh"
private
```

но имеет одно важное отличие.

Поле доступно не только внутри самого класса,

но и внутри его наследников.

Именно поэтому в классе

```ts id="b6r3cy"
CardPaymentProcessor
```

мы можем спокойно использовать

```ts id="z4k1fj"
this.merchantId
```

При этом внешний код по-прежнему не сможет обратиться к этому свойству напрямую.

---

То же самое относится и к методу

```ts id="p8m6qx"
protected validateAmount(...)
```

Он является частью внутренней реализации класса.

Наследники могут его использовать,

а внешний код — нет.

Это позволяет повторно использовать общую логику,

не делая ее частью публичного интерфейса класса.

---

Теперь посмотрим на реализацию метода оплаты.

```ts id="u2v9he"
override async pay(...)
```

Ключевое слово

```ts id="h7q3ln"
override
```

добавлено именно в TypeScript.

Оно явно показывает,

что метод переопределяет реализацию из родительского класса.

---

Можно ли написать метод без

```ts id="e5t8wc"
override
```

Да.

JavaScript прекрасно работает и без него.

Но использование этого ключевого слова делает код безопаснее.

Представьте,

что в базовом классе метод

```ts id="c4y2zb"
pay()
```

случайно переименовали.

Если

```ts id="s6m9pf"
override
```

не используется,

TypeScript может воспринять метод наследника как совершенно новый метод.

В результате переопределение перестанет работать так, как ожидалось.

Если же используется

```ts id="n8r1vd"
override
```

компилятор сразу обнаружит проблему и сообщит,

что в базовом классе больше нет метода для переопределения.

---

Во многих проектах включают настройку

```json id="t3k7au"
{
  "compilerOptions": {
    "noImplicitOverride": true
  }
}
```

После этого TypeScript требует,

чтобы каждое переопределение метода обязательно сопровождалось словом

```ts id="v9x5mc"
override
```

Если его забыть,

проект не скомпилируется.

Это помогает избежать ошибок во время рефакторинга больших проектов.

---

Итак,

в этом разделе мы познакомились сразу с несколькими возможностями TypeScript при работе с классами.

* **abstract class** запрещает создавать экземпляры базового класса.
* **abstract** метод задает контракт, который обязаны реализовать наследники.
* **protected** открывает доступ самому классу и его наследникам, но скрывает член от внешнего кода.
* **override** явно показывает, что метод переопределяет родительскую реализацию, а вместе с настройкой **noImplicitOverride** помогает компилятору находить ошибки при изменении кода.

Именно эти возможности TypeScript делают работу с наследованием более безопасной и понятной, не изменяя при этом сам механизм наследования JavaScript.

## 7. Интерфейс или абстрактный класс

Этот раздел я бы тоже сместил в сторону TypeScript. Не уходить в обсуждение принципов ООП, а ответить на практический вопрос, который возникает почти у каждого разработчика: **"Когда использовать `interface`, а когда `abstract class`?"**

---

## Сценарий урока

Мы уже знаем,

что TypeScript поддерживает абстрактные классы.

Но возникает закономерный вопрос.

Если в языке уже есть

```ts
abstract class
```

то зачем тогда нужен

```ts
interface
```

На самом деле эти конструкции решают разные задачи.

Начнем с интерфейса.

```ts id="k3p8vx"
interface PaymentGateway {
  pay(amount: number): Promise<{ transactionId: string }>;
  refund(transactionId: string): Promise<void>;
}
```

Интерфейс описывает только контракт.

То есть он отвечает на вопрос:

**какие методы должен иметь объект.**

Но совершенно ничего не говорит о том,

как эти методы должны работать.

---

Теперь посмотрим на класс.

```ts id="h7m2qd"
class TestPaymentGateway implements PaymentGateway {
  async pay(
    amount: number,
  ): Promise<{ transactionId: string }> {
    return { transactionId: `test-${amount}` };
  }

  async refund(_transactionId: string): Promise<void> {
    // Тестовая реализация.
  }
}
```

Ключевое слово

```ts id="x5n9lr"
implements
```

означает,

что класс обязуется реализовать контракт интерфейса.

Если забыть хотя бы один метод,

например,

```ts id="w2f8ca"
refund()
```

TypeScript сразу покажет ошибку.

Компилятор проверяет,

что класс полностью соответствует интерфейсу.

---

Обратите внимание,

интерфейс не содержит никакой реализации.

В нем находятся только объявления методов.

Например,

```ts id="z8q4mu"
pay(...)
```

и

```ts id="n6v3pk"
refund(...)
```

Все тело методов находится уже внутри класса.

---

Теперь вспомним предыдущий пример с абстрактным классом.

Там было иначе.

Мы могли написать готовый метод

```ts id="a4j7yn"
validateAmount()
```

и одновременно объявить абстрактный метод

```ts id="r1k5bt"
pay()
```

Получается,

что абстрактный класс может содержать и реализацию,

и состояние,

и обычные поля,

и конструктор.

Интерфейс всего этого не умеет.

Его задача —

описать форму объекта.

---

Есть еще одно важное отличие.

Класс может реализовать сразу несколько интерфейсов.

Например,

```ts id="p9m6cx"
class PaymentService
  implements PaymentGateway, Logger
```

Если оба интерфейса содержат разные контракты,

никаких проблем не возникает.

---

А вот наследоваться можно только от одного класса.

Например,

такая запись невозможна.

```ts id="u8q3we"
class PaymentService
  extends PaymentProcessor, BaseService
```

JavaScript поддерживает наследование только от одного базового класса.

Поэтому и TypeScript придерживается этого правила.

---

Возникает практический вопрос.

Что же использовать в своих проектах?

Если нужно просто описать,

какие методы или свойства должен иметь объект,

обычно выбирают

```ts id="m5v2rz"
interface
```

Если же требуется предоставить общую реализацию,

общие поля,

конструктор

или методы,

которые будут использовать все наследники,

используют

```ts id="d7k1fa"
abstract class
```

---

Можно запомнить простое правило.

**Интерфейс описывает контракт.**

**Абстрактный класс описывает общий фундамент для нескольких классов.**

Именно поэтому в TypeScript интерфейсы встречаются значительно чаще,

а абстрактные классы используют только тогда,

когда действительно нужно разделить общую реализацию между несколькими наследниками.

## 8. Обобщённый класс

Здесь тоже стоит сделать акцент на **дженериках в классах**, а не на паттерне Repository. Репозиторий — это всего лишь пример. Главная тема раздела — **обобщенные классы**.

---

## Сценарий урока

Мы уже использовали обобщения в функциях и типах.

Но TypeScript позволяет делать обобщенными и целые классы.

Рассмотрим пример.

```ts id="g8x4nr"
interface Entity {
  id: number;
}

class InMemoryRepository<T extends Entity> {
  private readonly items = new Map<number, T>();

  save(entity: T): void {
    this.items.set(entity.id, entity);
  }

  findById(id: number): T | undefined {
    return this.items.get(id);
  }

  findAll(): T[] {
    return [...this.items.values()];
  }

  remove(id: number): boolean {
    return this.items.delete(id);
  }
}
```

---

Сначала посмотрим на интерфейс.

```ts id="y5k2tv"
interface Entity {
  id: number;
}
```

Он описывает единственное обязательное свойство —

```ts id="c1m7pq"
id
```

Именно на него будет опираться наш класс.

---

Теперь обратим внимание на объявление класса.

```ts id="v4n8la"
class InMemoryRepository<T extends Entity>
```

Здесь используется знакомый нам параметр типа

```ts id="m9q3be"
T
```

Но рядом находится еще одна конструкция.

```ts id="r7k1xf"
extends Entity
```

Это ограничение типа.

Оно означает,

что вместо **T** можно подставить только такой тип,

который содержит свойство

```ts id="u2p6jd"
id: number
```

Именно поэтому внутри класса TypeScript разрешает обращаться к

```ts id="d8v5zn"
entity.id
```

без дополнительных проверок.

---

Например,

метод сохранения выглядит так.

```ts id="p4w1cy"
save(entity: T): void {
  this.items.set(entity.id, entity);
}
```

Компилятор знает,

что у любого объекта типа **T** обязательно существует свойство **id**.

---

Посмотрим на остальные методы.

```ts id="n6r2ka"
findById(id: number): T | undefined
```

Если объект найден,

метод возвращает именно тип **T**.

Если нет —

возвращает

```ts id="q3f8mw"
undefined
```

---

Метод

```ts id="t5j9rb"
findAll(): T[]
```

возвращает массив объектов того же типа,

который был передан при создании репозитория.

---

Теперь посмотрим,

как используется такой класс.

```ts id="w1x7pd"
type Task = {
  id: number;
  title: string;
  completed: boolean;
};
```

Создаем репозиторий.

```ts id="k8v4mh"
const taskRepository =
  new InMemoryRepository<Task>();
```

Что произошло?

TypeScript подставил вместо

```ts id="e7q2la"
T
```

тип

```ts id="z5m8cn"
Task
```

После этого все методы автоматически начинают работать именно с задачами.

Например,

```ts id="h9p6ry"
taskRepository.save({
  id: 1,
  title: "Изучить классы",
  completed: false,
});
```

Метод принимает только объекты типа

```ts id="j4n1bx"
Task
```

А

```ts id="s2k7ve"
findById()
```

вернет значение типа

```ts id="l6r9qt"
Task | undefined
```

без каких-либо дополнительных аннотаций.

---

А что произойдет,

если попробовать использовать тип,

у которого нет свойства

```ts id="x8m5df"
id
```

Например,

```ts id="c4p7nw"
type Category = {
  title: string;
};
```

и написать

```ts id="u1v8ke"
new InMemoryRepository<Category>();
```

TypeScript сразу сообщит об ошибке.

Тип

```ts id="f6q3mz"
Category
```

не удовлетворяет ограничению

```ts id="o9r2ta"
T extends Entity
```

потому что у него отсутствует обязательное свойство

```ts id="i5k4pv"
id
```

Именно это ограничение делает класс безопасным.

---

Важно понимать,

что в этом примере **репозиторий — лишь демонстрация**.

Главная идея раздела заключается в другом.

TypeScript позволяет делать обобщенными не только функции,

но и целые классы.

Благодаря этому один и тот же класс можно использовать с разными типами данных,

не теряя типизацию и не дублируя код.

Именно поэтому обобщенные классы часто встречаются в библиотеках, ORM, клиентах API и других универсальных компонентах.

## 9. Проблема растущей иерархии

Этот раздел я бы тоже немного перестроил. Здесь важно не читать лекцию по композиции как принципу ООП, а показать, **почему в проектах на TypeScript часто предпочитают композицию наследованию**. Тогда это будет логичным продолжением темы классов.

---

## Сценарий урока

До этого момента мы рассматривали наследование.

Но в реальных TypeScript-проектах гораздо чаще можно встретить другой подход —

**композицию**.

Причина довольно простая.

С ростом числа наследников иерархия классов быстро становится слишком сложной.

Представим, что мы разрабатываем систему уведомлений.

Сначала появляется обычный класс.

```text
EmailNotification
```

Затем возникает необходимость отправлять срочные письма.

```text
UrgentEmailNotification
```

Потом требуется повторная отправка при ошибке.

```text
RetryingEmailNotification
```

А если письмо должно быть одновременно срочным и с повторными попытками?

Появляется еще один класс.

```text
UrgentRetryingEmailNotification
```

И это только две дополнительные возможности.

Каждая новая независимая функция приводит к появлению новых комбинаций,

а вместе с ними — новых классов.

Иерархия начинает быстро разрастаться.

---

Вместо этого в TypeScript часто используют композицию.

Идея очень простая.

Большой класс не наследует множество вариантов поведения,

а получает необходимые компоненты извне.

Посмотрим на пример.

```ts id="j3k7na"
interface Sender {
  send(recipient: string, message: string): Promise<void>;
}

interface MessageFormatter {
  format(subject: string, body: string): string;
}

interface RetryPolicy {
  execute(operation: () => Promise<void>): Promise<void>;
}

class NotificationService {
  constructor(
    private readonly sender: Sender,
    private readonly formatter: MessageFormatter,
    private readonly retryPolicy: RetryPolicy,
  ) {}

  async notify(
    recipient: string,
    subject: string,
    body: string,
  ): Promise<void> {
    const message = this.formatter.format(subject, body);

    await this.retryPolicy.execute(() =>
      this.sender.send(recipient, message),
    );
  }
}
```

---

Начнем с интерфейсов.

```ts id="p4m2ry"
interface Sender
```

описывает способ отправки сообщения.

Это может быть электронная почта,

SMS,

мессенджер

или любой другой канал.

---

Следующий интерфейс —

```ts id="t8q5vd"
interface MessageFormatter
```

Он отвечает только за форматирование текста.

Например,

можно сделать HTML-письмо,

обычный текст

или Markdown.

---

Последний интерфейс —

```ts id="h6r1cx"
interface RetryPolicy
```

Он определяет,

что делать,

если отправка завершилась ошибкой.

Можно вообще не выполнять повторную попытку,

можно повторить один раз,

а можно использовать более сложную стратегию.

---

Теперь посмотрим на сам класс.

```ts id="y2k8pf"
class NotificationService
```

Обратите внимание,

что он не наследуется ни от какого базового класса.

Вместо этого все необходимые зависимости передаются через конструктор.

```ts id="m7v4qa"
constructor(
  private readonly sender: Sender,
  private readonly formatter: MessageFormatter,
  private readonly retryPolicy: RetryPolicy,
)
```

Каждая зависимость отвечает только за одну задачу.

---

Когда вызывается метод

```ts id="r5n9lb"
notify(...)
```

происходит последовательность простых действий.

Сначала форматируется сообщение.

```ts id="x1c6jt"
const message =
  this.formatter.format(subject, body);
```

Затем выполняется отправка.

```ts id="s8p2mw"
this.sender.send(recipient, message)
```

А политика повторных попыток решает,

нужно ли повторять операцию при ошибке.

```ts id="q4d7he"
this.retryPolicy.execute(...)
```

Каждый компонент занимается только своей задачей.

---

Главное преимущество такого подхода —

гибкость.

Можно заменить только отправителя,

не меняя форматирование.

Можно заменить только стратегию повторных попыток.

Можно использовать любую комбинацию компонентов,

не создавая новые классы-наследники.

---

Есть и еще одно преимущество,

которое особенно важно для TypeScript.

Все зависимости представлены интерфейсами.

Это означает,

что в тестах можно легко подставить тестовые реализации.

Например,

вместо настоящего отправителя использовать объект,

который просто запоминает отправленные сообщения,

не обращаясь к реальному почтовому серверу.

---

Именно поэтому в современных TypeScript-проектах композиция встречается значительно чаще наследования.

Наследование остается полезным инструментом,

но если класс начинает обрастать множеством специализированных наследников,

обычно стоит задуматься,

не лучше ли разделить его поведение на независимые компоненты и объединить их с помощью композиции.

## 10. Мини-проект: менеджер задач

Этот раздел я бы немного изменил по смыслу. Сейчас название **«Мини-проект»** хорошее, но рассказ снова может уйти в ООП. А лучше показать студенту, **как все изученные возможности TypeScript объединяются в одном классе**.

---

## Сценарий урока

Давайте объединим все возможности, которые мы изучили в этом уроке, в одном небольшом примере.

Перед нами класс, описывающий задачу в менеджере задач.

```ts id="q7k4mz"
type TaskStatus = "todo" | "inProgress" | "done";

class TaskEntity {
  private status: TaskStatus = "todo";

  constructor(
    public readonly id: number,
    private title: string,
  ) {
    if (title.trim() === "") {
      throw new Error("Название задачи обязательно");
    }
  }

  rename(title: string): void {
    if (title.trim() === "") {
      throw new Error("Название задачи обязательно");
    }

    this.title = title.trim();
  }

  start(): void {
    if (this.status !== "todo") {
      throw new Error("Начать можно только новую задачу");
    }

    this.status = "inProgress";
  }

  complete(): void {
    if (this.status !== "inProgress") {
      throw new Error("Завершить можно только активную задачу");
    }

    this.status = "done";
  }

  toSnapshot(): {
    id: number;
    title: string;
    status: TaskStatus;
  } {
    return {
      id: this.id,
      title: this.title,
      status: this.status,
    };
  }
}
```

---

Начнем с типа статуса.

```ts id="b5n8tr"
type TaskStatus =
  | "todo"
  | "inProgress"
  | "done";
```

Мы уже использовали литеральные объединения в предыдущих уроках.

Поэтому поле статуса может принимать только одно из трех заранее известных значений.

Попытка присвоить любое другое значение сразу приведет к ошибке TypeScript.

---

Теперь посмотрим на объявление класса.

```ts id="w2m7cq"
class TaskEntity
```

Сразу можно заметить знакомые конструкции.

В конструкторе используются **parameter properties**.

```ts id="h9k3va"
public readonly id: number,
private title: string,
```

TypeScript автоматически создает соответствующие свойства класса и сохраняет в них переданные значения.

---

Поле

```ts id="x4r8ld"
status
```

объявлено отдельно.

```ts id="p7f2zn"
private status: TaskStatus = "todo";
```

При создании новой задачи она автоматически получает статус

```ts id="u5m9bc"
"todo"
```

Внешний код не может изменить это поле напрямую,

потому что оно объявлено как

```ts id="a3k6qp"
private
```

---

Обратите внимание,

что конструктор сразу выполняет проверку.

```ts id="c8v1jy"
if (title.trim() === "") {
  throw new Error(...);
}
```

Если название пустое,

объект вообще не будет создан.

---

Точно такая же проверка используется и в методе

```ts id="m6r4xt"
rename()
```

Нельзя переименовать задачу в пустую строку.

---

Самое интересное происходит при изменении статуса.

Метод

```ts id="r1p9wk"
start()
```

разрешает переводить задачу в работу только из состояния

```ts id="z2n5cf"
"todo"
```

Если попытаться запустить уже выполняющуюся

или завершенную задачу,

будет выброшена ошибка.

---

А метод

```ts id="k7m3yb"
complete()
```

разрешает завершить задачу только тогда,

когда она уже находится в состоянии

```ts id="t9q6xe"
"inProgress"
```

Получается,

что изменить статус можно только через специальные методы класса,

которые проверяют допустимость переходов.

---

Последний метод называется

```ts id="e4w8pn"
toSnapshot()
```

Он возвращает обычный объект.

```ts id="g2v7ma"
{
  id,
  title,
  status
}
```

Такой объект легко сериализовать,

например,

преобразовать в JSON,

сохранить в файл

или отправить по сети.

При этом внешний код получает только копию данных,

а не доступ к приватным полям класса.

---

Если посмотреть на этот пример целиком,

можно увидеть сразу несколько возможностей TypeScript,

которые мы изучили в этом уроке.

* **parameter properties** сокращают объявление свойств;
* **readonly** защищает идентификатор от изменения;
* **private** скрывает внутреннее состояние объекта;
* литеральное объединение **TaskStatus** ограничивает допустимые значения статуса;
* типы методов и возвращаемых значений проверяются компилятором.

Получился небольшой,

но вполне реалистичный пример,

в котором разные возможности TypeScript работают вместе и помогают сделать код безопаснее и понятнее.
