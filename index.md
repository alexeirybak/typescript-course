# Урок 10. Дженерики: сохраняем связи между типами

Дженерик — это не верх профессионального мастерства в TypeScript, и не «тип, который принимает всё». Это способ отложить выбор конкретного типа и сохранить отношения между несколькими позициями контракта.

## 1. Проблема потери информации

До этого момента мы всегда явно указывали типы.

Например, писали `string`, `number`, `User`, `Product`.

Но очень часто возникает совсем другая задача.

Мы заранее не знаем, с каким типом будет работать функция.

Она должна одинаково хорошо работать и со строками, и с числами, и с объектами.

Первое желание — использовать `unknown`.

Покажу простой пример.

Есть функция, которая возвращает первый элемент массива.

```ts
function firstUnknown(items: unknown[]): unknown {
  return items[0];
}

const value = firstUnknown(["Анна", "Борис"]);
```

Передали массив строк.

Логично ожидать, что обратно получим строку.

Но если навести курсор на переменную `value`, TypeScript показывает:

```ts
unknown
```

Почему?

Потому что функция знает только одно:

«Мне дали массив каких-то неизвестных значений.»

Она действительно не знает, были это строки, числа или объекты.

Поэтому и возвращает `unknown`.

Получается странная ситуация.

Мы сами прекрасно понимаем, что передали строки.

Но TypeScript эту информацию потерял.

Именно это называется **потерей информации о типе**.

---

Некоторые разработчики в этот момент говорят:

«Ну тогда давайте использовать `any`.»

Давайте посмотрим.

```ts
function firstAny(items: any[]): any {
  return items[0];
}

const unsafe = firstAny(["Анна"]);
unsafe.nonExistingMethod();
```

На первый взгляд всё стало лучше.

Исчезли ошибки.

Но это ложное ощущение безопасности.

Если вызвать несуществующий метод...

```ts
unsafe.nonExistingMethod();
```

...TypeScript ничего не скажет.

Хотя во время выполнения приложение просто упадёт.

Получается интересная картина.

`unknown` слишком осторожный.

Он всё запрещает.

`any`, наоборот, разрешает вообще всё.

Но ни один из них не решает нашу настоящую проблему.

Мы хотим не убрать проверки.

Мы хотим, чтобы TypeScript **запомнил**, какой тип пришёл в функцию.

---

И вот здесь появляются дженерики.

Посмотрите на новую версию.

```ts
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}
```

Пока не обращайте внимания на букву `T`.

Сейчас важно понять саму идею.

`T` — это не конкретный тип.

Это место, которое позже будет заполнено настоящим типом.

Теперь вызываем функцию.

```ts
const firstName = first(["Анна", "Борис"]);
```

Наводим курсор.

TypeScript показывает:

```ts
string | undefined
```

Попробуем числа.

```ts
const firstNumber = first([10, 20]);
```

Получаем:

```ts
number | undefined
```

А если передать объекты...

```ts
const firstUser = first([
  { id: 1, name: "Анна" },
  { id: 2, name: "Борис" },
]);
```

То результатом станет

```ts
{
    id: number;
    name: string;
} | undefined
```

Мы вообще нигде не писали слово `string`.

Не писали `number`.

Не описывали объект.

TypeScript сам посмотрел на аргумент функции и сделал вывод, какой тип нужно подставить вместо `T`.

---

Именно это и является главной идеей дженериков.

Они не делают функцию более универсальной сами по себе.

Они позволяют **сохранить связь** между типами.

Тип элементов массива связан с типом возвращаемого значения.

Если изменится входной тип — автоматически изменится и выходной.

Эта связь и делает дженерики настолько мощным инструментом.

Практически весь современный TypeScript построен именно на сохранении подобных связей между входными и выходными типами.

В следующих разделах мы научимся создавать такие связи самостоятельно и увидим, что большинство библиотек TypeScript используют именно этот механизм.


## 2. Явный и выведенный параметр типа

Этот вопрос лучше построить на продолжении предыдущего примера. Не вводить новую функцию, а показать, что у зрителя наверняка уже возник вопрос: **«Откуда TypeScript вообще узнал, что `T` — это `string`?»** Именно на него и отвечает эта часть урока.


В предыдущем примере мы несколько раз вызывали функцию `first`.

```ts
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}
```

И каждый раз происходило что-то интересное.

Когда мы передали строки...

```ts
const firstName = first(["Анна", "Борис"]);
```

...TypeScript решил, что `T` — это `string`.

Когда передали числа...

```ts
const firstNumber = first([10, 20]);
```

...он автоматически выбрал `number`.

Возникает вполне логичный вопрос.

Откуда TypeScript вообще знает, какой тип нужно подставить вместо `T`?

---

Ответ очень простой.

Он смотрит на аргументы функции.

В нашем случае массив содержит строки.

Значит, элементы имеют тип `string`.

Следовательно,

```text
T = string
```

Если массив содержит числа —

```text
T = number
```

Если объекты —

```text
T = объект
```

То есть чаще всего TypeScript **сам выводит параметр типа**.

Этот процесс называется **type inference** — вывод типов.

Поэтому мы почти никогда не пишем `T` самостоятельно.

---

Давайте еще раз посмотрим на вызов.

```ts
const name = first(["Анна", "Борис"]);
```

Если навести курсор на функцию...

VS Code покажет примерно такую картину.

```text
first<string>(...)
```

Обратите внимание.

Мы нигде не написали слово `string`.

Но редактор уже знает, что именно его компилятор подставил вместо `T`.

Это произошло автоматически.

---

Но возникает другой вопрос.

Всегда ли TypeScript способен вывести тип самостоятельно?

Нет.

Есть ситуации, когда информации недостаточно.

Самый простой пример — пустой массив.

```ts
const maybeName = first([]);
```

Попробуйте написать такой код.

И посмотрите, что произошло.

Откуда компилятору узнать, какого типа элементы должны были находиться внутри?

Строки?

Числа?

Пользователи?

Товары?

Пока массив пустой, никаких подсказок нет.

---

Именно в таких случаях параметр типа можно указать самостоятельно.

```ts
const maybeName = first<string>([]);
```

Теперь мы явно говорим компилятору:

«Считай, что этот массив предназначен для строк.»

Поэтому результатом станет

```ts
string | undefined
```

Даже несмотря на то, что массив пока пустой.

---

Здесь важно понять одну вещь.

Запись

```ts
first<string>(...)
```

не преобразует данные.

Она ничего не приводит и ничего не меняет во время выполнения программы.

Мы просто сообщаем компилятору, какой тип нужно использовать вместо `T`.

В JavaScript этого вообще не существует.

После компиляции эта запись полностью исчезает.

---

Стоит ли всегда писать параметр типа вручную?

Обычно — нет.

Например, такой код

```ts
const firstName = first<string>(["Анна", "Борис"]);
```

полностью корректный.

Но возникает вопрос.

Зачем?

TypeScript и так безошибочно определил, что здесь строки.

Мы просто дублируем информацию.

Лишний код не делает программу понятнее.

Наоборот, он увеличивает количество того, что придется поддерживать.

---

Поэтому существует хорошее практическое правило.

Если TypeScript смог самостоятельно вывести тип — не мешайте ему.

Если информации недостаточно — например, при работе с пустыми массивами, некоторыми фабриками, сложными дженериками или неоднозначными выражениями — тогда параметр типа можно указать явно.

Именно так дженерики чаще всего используются в реальных проектах.


## 3. Несколько параметров

Этот вопрос логично начать с мысли: **до сих пор у нас был всего один параметр типа, но что делать, если нужно сохранить сразу несколько независимых связей?** Тогда появление `TFirst`, `TSecond`, `TInput` и `TOutput` выглядит совершенно естественно.

До этого момента у нас был всего один параметр типа.

```ts id="g3k1pa"
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}
```

Это было логично.

В функции существовал только один неизвестный тип — тип элементов массива.

Поэтому одного параметра `T` было вполне достаточно.

Но в реальной разработке очень часто приходится работать сразу с несколькими разными типами.

Например, один аргумент — строка.

Другой — число.

И между ними тоже нужно сохранить правильные связи.

---

Представим функцию, которая объединяет два значения в кортеж.

```ts id="p9g5xo"
function pair<TFirst, TSecond>(
  first: TFirst,
  second: TSecond,
): [TFirst, TSecond] {
  return [first, second];
}
```

Обратите внимание.

Теперь появился уже не один параметр типа.

Их два.

`TFirst` отвечает за первый аргумент.

`TSecond` — за второй.

Каждый выводится независимо.

---

Посмотрим на вызов.

```ts id="t8q4kw"
const entry = pair("age", 30);
```

Что происходит?

Для первого аргумента TypeScript видит строку.

Поэтому

```text id="m3z7ha"
TFirst = string
```

Для второго аргумента он видит число.

Поэтому

```text id="r5a1qp"
TSecond = number
```

Теперь посмотрим на результат.

Если навести курсор на `entry`, увидим

```ts id="n7l2uv"
[string, number]
```

Именно этого мы и ожидали.

Заметьте, мы нигде не писали эти типы вручную.

Компилятор снова всё вывел самостоятельно.

---

Конечно, подобная функция сама по себе не очень впечатляет.

Но она показывает важную идею.

Количество параметров типа не ограничено одним.

Их может быть два...

Три...

Четыре...

Столько, сколько действительно требуется функции.

Главное — чтобы каждый из них описывал свою собственную связь.

---

Теперь посмотрим пример, который уже гораздо ближе к реальным библиотекам.

Напишем собственную функцию преобразования массива.

```ts id="u5d9cm"
function mapArray<TInput, TOutput>(
  items: readonly TInput[],
  transform: (item: TInput, index: number) => TOutput,
): TOutput[] {
  return items.map(transform);
}
```

На первый взгляд параметров стало заметно больше.

Но если разобраться, всё очень логично.

---

Первый параметр типа —

```text id="8i6vjt"
TInput
```

— описывает элементы входного массива.

Именно этот тип используется сразу в двух местах.

Во-первых, в самом массиве.

```ts id="k2p4yb"
items: readonly TInput[]
```

Во-вторых, в параметре callback.

```ts id="d7m3qx"
(item: TInput)
```

Это одна и та же информация.

Поэтому используется один и тот же параметр типа.

---

Второй параметр —

```text id="h1r8zs"
TOutput
```

— описывает результат работы callback.

Именно этот тип возвращает функция преобразования.

```ts id="q6x5ln"
(item) => TOutput
```

И именно из таких значений затем состоит новый массив.

```ts id="a9f2ke"
TOutput[]
```

Получается, что один параметр типа связывает входные данные.

Другой — выходные.

---

Теперь вызовем функцию.

```ts id="w4n8ci"
const lengths = mapArray(
  ["TypeScript", "React"],
  (word) => word.length,
);
```

Разберём, что делает TypeScript.

Он видит массив строк.

Следовательно,

```text id="v2q6mr"
TInput = string
```

Затем анализирует callback.

```ts id="b8j4sd"
(word) => word.length
```

`length` возвращает число.

Поэтому

```text id="e5u1ka"
TOutput = number
```

А раз элементы после преобразования имеют тип `number`,

то итоговая функция возвращает

```ts id="f3y9pl"
number[]
```

Именно это и покажет редактор.

---

Обратите внимание на самое важное.

TypeScript самостоятельно связал сразу четыре разных места:

* тип элементов входного массива;
* тип параметра `word` внутри callback;
* тип результата callback;
* тип элементов итогового массива.

Мы нигде не написали ни `string`, ни `number`.

Всё получилось автоматически благодаря двум параметрам типа.

---

Именно поэтому современные библиотеки вроде React, TanStack Query, Redux Toolkit и многих других активно используют несколько параметров типа одновременно.

Они позволяют сохранить связи между различными частями программы, чтобы компилятор мог автоматически вывести правильные типы и защитить нас от ошибок без необходимости писать их вручную.


## 4. Ограничения через extends

Этот вопрос лучше начать с распространённого заблуждения. После первых примеров с дженериками у многих появляется мысль: **«Раз у меня есть `T`, значит я могу обращаться к любым его свойствам».** Именно здесь и появляется необходимость в `extends`.

До этого момента все наши параметры типа были полностью свободными.

Например, вот такая функция.

```ts id="r2g7xm"
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}
```

Или функция преобразования массива.

```ts id="d8n4qw"
function mapArray<TInput, TOutput>(
  items: readonly TInput[],
  transform: (item: TInput) => TOutput,
): TOutput[] {
  return items.map(transform);
}
```

Во всех этих примерах TypeScript вообще ничего не знает о типе `T`.

Он знает только одно.

Это какой-то тип.

Не более.

---

Предположим, мы захотели написать функцию, которая выводит идентификатор объекта.

Первая попытка может выглядеть так.

```ts id="m5u9ka"
function logIdBroken<T>(value: T): void {
  console.log(value.id);
}
```

Попробуем сохранить файл.

И сразу получим ошибку.

Почему?

---

Причина очень простая.

Для компилятора параметр типа `T` может оказаться чем угодно.

Например,

```ts id="p4x6jr"
logIdBroken(100);
```

или

```ts id="v8c3he"
logIdBroken("Hello");
```

или

```ts id="t1q7nb"
logIdBroken(true);
```

Есть ли у числа свойство `id`?

Нет.

У строки?

Тоже нет.

У логического значения?

Тем более нет.

Поэтому TypeScript совершенно справедливо запрещает обращаться к такому свойству.

Компилятор не знает, существует оно вообще или нет.

---

Получается интересная ситуация.

Мы хотим работать не с любым типом.

А только с теми объектами, у которых есть поле `id`.

Как объяснить это TypeScript?

---

Для начала опишем минимальный контракт.

```ts id="k7m2zs"
type HasId = {
  id: string | number;
};
```

Это единственное требование.

Нас пока не интересуют остальные свойства объекта.

Важно только наличие идентификатора.

---

Теперь добавим ограничение.

```ts id="y3p8lu"
function logId<T extends HasId>(value: T): T {
  console.log(value.id);
  return value;
}
```

Посмотрите внимательно на запись.

```ts id="f6w1oq"
T extends HasId
```

Очень важно правильно понимать слово `extends`.

Здесь оно **не имеет никакого отношения к наследованию классов**.

В дженериках смысл совсем другой.

Эта запись означает:

> Тип `T` должен как минимум соответствовать контракту `HasId`.

Именно "как минимум".

Он может содержать гораздо больше свойств.

---

Теперь вызовем функцию.

```ts id="n9r4xa"
const product = logId({
  id: 1,
  title: "Клавиатура",
  price: 7500,
});
```

Что происходит?

TypeScript проверяет объект.

Есть ли поле `id`?

Есть.

Причём его тип подходит.

Значит, объект удовлетворяет ограничению.

Функцию можно вызвать.

---

Но здесь есть очень важный момент.

Посмотрите, что находится в переменной `product`.

Многие новички ожидают увидеть тип

```ts id="u4k8mi"
HasId
```

Но это неверно.

Если навести курсор, окажется, что TypeScript сохранил полный тип объекта.

То есть здесь доступны все свойства.

Например,

```ts id="e2v5cp"
console.log(product.title);
```

никакой ошибки не возникает.

Почему?

Потому что функция возвращает не `HasId`.

Она возвращает именно `T`.

А `T` в данном вызове — это весь объект целиком.

Ограничение проверяло лишь наличие обязательного поля `id`, но не заменяло исходный тип на `HasId`.

---

Это одна из самых сильных сторон дженериков.

Ограничение проверяет минимальные требования.

Но при этом TypeScript сохраняет всю дополнительную информацию о типе.

Именно поэтому мы можем спокойно обращаться и к `title`, и к `price`, и к любым другим свойствам объекта.

---

Запомните практическое правило.

Если функция должна работать абсолютно с любым типом — используйте свободный параметр типа.

Если же функции требуется, чтобы у типа обязательно были определённые свойства или методы, добавьте ограничение через `extends`.

Тогда TypeScript сможет безопасно использовать эти свойства, не теряя при этом информацию о полном типе объекта.


## 5. keyof и связанные ключи

Этот вопрос — один из самых важных в теме дженериков. Но его лучше не начинать с объяснения `keyof`. Сначала нужно показать проблему: **почему обычная функция поиска свойства оказывается практически бесполезной**. Тогда появление `keyof` выглядит естественным решением.

До этого момента мы связывали между собой разные типы.

Например, входной массив и результат функции.

Или объект и его обязательное свойство `id`.

Но очень часто возникает другая задача.

Есть объект.

Есть имя его свойства.

И хочется получить значение этого свойства так, чтобы TypeScript точно знал его тип.

---

Первая попытка обычно выглядит примерно так.

```ts id="v3n7ka"
function getPropertyUnsafe(
  object: object,
  key: string,
): unknown {
  return (object as Record<string, unknown>)[key];
}
```

На первый взгляд всё работает.

Передаём объект.

Передаём строку.

Получаем значение.

Но проблема здесь сразу в двух местах.

---

Во-первых,

ключ имеет тип

```ts id="u6m1px"
string
```

То есть функция принимает абсолютно любую строку.

Даже такую, которой в объекте вообще нет.

Компилятор ничего не сможет сказать.

---

Во-вторых,

результат имеет тип

```ts id="b9q4lc"
unknown
```

Мы снова потеряли всю информацию.

Функция достала значение.

Но TypeScript уже не понимает, что именно было получено.

Практически та же проблема, которую мы рассматривали в самом начале урока.

---

Получается, нам нужно сохранить сразу две связи.

Первая.

Ключ должен существовать в объекте.

Вторая.

Тип результата должен зависеть именно от выбранного ключа.

Именно это позволяют сделать дженерики.

---

Посмотрите на новую функцию.

```ts id="h2k8wy"
function getProperty<T, K extends keyof T>(
  object: T,
  key: K,
): T[K] {
  return object[key];
}
```

На первый взгляд запись выглядит пугающе.

Но если разобрать её по частям, всё становится очень логичным.

---

Первый параметр уже знаком.

```ts id="x7v5md"
T
```

Это тип объекта.

Например,

```ts id="n1p6qs"
{
  id: number;
  name: string;
  active: boolean;
}
```

---

Дальше появляется новое выражение.

```ts id="r4j9eu"
keyof T
```

Оператор `keyof` создаёт объединение всех ключей объекта.

Если взять такой объект

```ts id="k8m3zf"
const user = {
  id: 1,
  name: "Анна",
  active: true,
};
```

то

```text id="p5t2ca"
keyof typeof user
```

превратится в

```ts id="q9x7lr"
"id" | "name" | "active"
```

То есть получится объединение всех допустимых ключей.

---

Теперь посмотрим на второй параметр типа.

```ts id="d6w8hk"
K extends keyof T
```

Это означает:

`K` может быть только одним из существующих ключей объекта.

Не любой строкой.

А только допустимым ключом.

Именно поэтому параметр функции записан так.

```ts id="e3n4mv"
key: K
```

---

Остаётся последний элемент.

Тип результата.

```ts id="a7c2py"
T[K]
```

Это специальная конструкция TypeScript.

Она означает:

«Возьми тип объекта `T` и верни тип свойства с ключом `K`.»

Именно благодаря этому результат зависит от выбранного ключа.

---

Давайте посмотрим на практике.

```ts id="m8q5tu"
const user = {
  id: 1,
  name: "Анна",
  active: true,
};
```

Получим имя пользователя.

```ts id="f2r6kd"
const userName = getProperty(user, "name");
```

Если навести курсор...

увидим

```ts id="y5v9hb"
string
```

Почему?

Потому что свойство `name` имеет тип `string`.

---

Теперь возьмём другое поле.

```ts id="g4x1pm"
const active = getProperty(user, "active");
```

Теперь TypeScript показывает

```ts id="w8n3js"
boolean
```

Мы ничего не меняли в функции.

Изменился только ключ.

И вместе с ним автоматически изменился тип результата.

Именно этого мы и добивались.

---

А теперь попробуем обратиться к несуществующему свойству.

```ts id="t6p8cq"
getProperty(user, "email");
```

И сразу получим ошибку компиляции.

Почему?

Потому что ключ `"email"` отсутствует в объединении

```ts id="c1m7zu"
"id" | "name" | "active"
```

TypeScript обнаружил проблему ещё до запуска программы.

---

Давайте ещё раз подведём итог.

В этой функции каждый элемент отвечает за свою задачу.

`T` — это тип объекта.

`keyof T` — множество всех допустимых ключей этого объекта.

`K` — конкретный ключ, который выбрал разработчик.

А `T[K]` — тип значения, которое находится по этому ключу.

---

Это один из самых распространённых шаблонов во всём TypeScript.

Именно его используют многие современные библиотеки, когда позволяют безопасно получать свойства объектов, работать с конфигурациями, формами, состояниями и другими структурами данных.

Поэтому конструкцию

```ts
T,
K extends keyof T,
T[K]
```

стоит хорошо запомнить — вы будете встречать её очень часто.

## 6. Обновление свойства

Логично продолжить предыдущий пример. Там мы научились безопасно **получать** значение свойства. Теперь сделаем следующий шаг — научимся безопасно это свойство **изменять**, сохраняя связь между ключом и типом нового значения.

В предыдущем вопросе мы создали функцию `getProperty`.

```ts
function getProperty<T, K extends keyof T>(
  object: T,
  key: K,
): T[K] {
  return object[key];
}
```

Она безопасно получает значение по ключу.

TypeScript проверяет две вещи:

ключ действительно существует в объекте;

тип результата соответствует выбранному свойству.

Теперь представим обратную задачу.

Нам нужно изменить одно из свойств объекта.

---

Наивная версия могла бы выглядеть так:

```ts
function setPropertyUnsafe(
  object: object,
  key: string,
  value: unknown,
): object {
  return {
    ...object,
    [key]: value,
  };
}
```

Технически такая функция работает.

Но TypeScript почти ничем нам не помогает.

Он не проверяет, существует ли ключ.

И не проверяет, подходит ли новое значение для выбранного свойства.

Например, мы можем попытаться записать строку в поле, где ожидается `boolean`.

Компилятор этого не заметит.

---

Используем уже знакомую связь между объектом и его ключом.

```ts
function setProperty<T, K extends keyof T>(
  object: T,
  key: K,
  value: T[K],
): T {
  return {
    ...object,
    [key]: value,
  };
}
```

На первый взгляд эта функция почти повторяет предыдущую.

Но здесь появляется новый важный элемент:

```ts
value: T[K]
```

Именно он связывает новое значение с выбранным ключом.

---

Разберём параметры по порядку.

```ts
object: T
```

`T` — полный тип объекта.

Например, для нашего пользователя TypeScript выводит примерно такой тип:

```ts
{
  id: number;
  name: string;
  active: boolean;
}
```

---

Следующий параметр:

```ts
key: K
```

При этом `K` ограничен:

```ts
K extends keyof T
```

Значит, ключом может быть только реально существующее свойство объекта.

Для `user` это:

```ts
"id" | "name" | "active"
```

---

И теперь главное:

```ts
value: T[K]
```

Тип `value` зависит от того, какой ключ был выбран.

Если выбран ключ `"active"`, TypeScript вычисляет:

```ts
T["active"]
```

Получается:

```ts
boolean
```

Следовательно, третьим аргументом можно передать только логическое значение.

---

Посмотрим на вызов.

```ts
const updatedUser = setProperty(user, "active", false);
```

TypeScript выполняет несколько шагов.

Сначала определяет тип объекта:

```text
T = typeof user
```

Затем видит ключ:

```text
K = "active"
```

После этого вычисляет тип значения:

```text
T[K] = T["active"] = boolean
```

Поэтому значение `false` подходит.

---

Если навести курсор на `updatedUser`, мы увидим, что функция возвращает полный тип пользователя.

```ts
{
  id: number;
  name: string;
  active: boolean;
}
```

Информация об остальных свойствах не потерялась.

---

Теперь попробуем передать неправильное значение.

```ts
setProperty(user, "active", "yes");
```

Получим ошибку.

Потому что для свойства `"active"` ожидается `boolean`, а мы передали `string`.

В учебном примере можно зафиксировать ожидаемую ошибку:

```ts
// @ts-expect-error: active ожидает boolean
setProperty(user, "active", "yes");
```

Комментарий `@ts-expect-error` сообщает TypeScript:

«На следующей строке ошибка сделана намеренно».

Если ошибка действительно есть, компилятор пропустит этот пример.

Если ошибка неожиданно исчезнет, TypeScript сообщит, что директива больше не нужна.

---

Попробуем обновить другие свойства.

```ts
const renamedUser = setProperty(user, "name", "Мария");
```

Здесь ключ `"name"` связан с типом `string`.

Поэтому строка подходит.

```ts
const changedId = setProperty(user, "id", 2);
```

Для `"id"` ожидается `number`.

Число тоже подходит.

А такой код уже будет ошибочным:

```ts
// @ts-expect-error: id ожидает number
setProperty(user, "id", "2");
```

---

Обратите внимание и на реализацию функции.

```ts
return {
  ...object,
  [key]: value,
};
```

Мы не изменяем исходный объект напрямую.

Сначала копируем его свойства через оператор расширения:

```ts
...object
```

Затем перезаписываем выбранное свойство:

```ts
[key]: value
```

В результате возвращается новый объект.

---

Здесь дженерики связывают уже три позиции контракта:

```ts
object: T
key: K
value: T[K]
```

Объект определяет набор допустимых ключей.

Выбранный ключ определяет допустимый тип значения.

Именно поэтому одна функция безопасно работает со всеми свойствами объекта, хотя их типы могут быть совершенно разными.

Главная мысль этого вопроса:

```text
Тип значения зависит от выбранного ключа.
```

Мы не просто разрешаем передать какое-то значение.

Мы требуем именно тот тип, который соответствует конкретному свойству объекта.


## 7. Generic-интерфейсы

Этот вопрос логично начать с наблюдения: **до сих пор мы использовали дженерики только в функциях, но ведь типы данных тоже часто приходится делать универсальными**. Именно отсюда естественно появляется идея generic-интерфейсов и generic-типов.


До этого момента все дженерики находились внутри функций.

Например,

```ts
function first<T>(...)
```

или

```ts
function mapArray<TInput, TOutput>(...)
```

Идея была простой.

Функция должна была одинаково хорошо работать с разными типами данных.

Но возникает вопрос.

А если универсальной должна быть не функция, а сам тип данных?

---

Представьте, что приложение обращается к серверу.

Сегодня сервер возвращает пользователей.

Завтра — товары.

Послезавтра — список заказов.

Во всех случаях структура ответа почти одинаковая.

Отличаются только сами данные.

---

Первое желание — использовать `any`.

Например,

```ts
type ApiResponse = {
  status: string;
  data: any;
};
```

Такой тип действительно подходит для любых данных.

Но есть серьёзная проблема.

Полностью исчезает информация о содержимом поля `data`.

TypeScript больше не сможет проверить, что именно там находится.

---

Можно использовать `unknown`.

Это безопаснее.

Но тогда после каждого обращения придётся самостоятельно выполнять проверки типов.

Получается неудобно.

---

Нам хочется другого.

Чтобы структура ответа была общей.

А тип данных внутри неё менялся автоматически.

Именно для этого используются generic-типы.

---

Посмотрите на определение.

```ts
type ApiSuccess<T> = {
  status: "success";
  data: T;
};
```

Здесь уже знакомый параметр типа `T`.

Только теперь он находится не в функции, а внутри типа.

Поле

```ts
data
```

имеет тип `T`.

То есть конкретный тип данных будет выбран позже.

---

Теперь опишем вариант ошибки.

```ts
type ApiFailure = {
  status: "error";
  message: string;
};
```

Здесь никаких дженериков уже не требуется.

Если произошла ошибка, никаких данных нет.

Есть только сообщение.

---

Теперь объединим оба варианта.

```ts
type ApiResponse<T> =
  | ApiSuccess<T>
  | ApiFailure;
```

Получился универсальный тип ответа сервера.

Обратите внимание.

Параметр `T` автоматически передаётся внутрь `ApiSuccess`.

То есть связь сохраняется.

---

Давайте создадим собственный тип пользователя.

```ts
type User = {
  id: number;
  name: string;
};
```

Теперь объявим ответ сервера.

```ts
const response: ApiResponse<User[]> = {
  status: "success",
  data: [
    {
      id: 1,
      name: "Анна",
    },
  ],
};
```

Посмотрите внимательно.

Мы написали

```ts
ApiResponse<User[]>
```

Это означает:

вместо `T` нужно использовать массив пользователей.

То есть

```text
T = User[]
```

---

Что получится после такой подстановки?

TypeScript фактически увидит примерно такую структуру.

```ts
type ApiSuccess = {
  status: "success";
  data: User[];
};
```

Именно поэтому внутри массива разрешены только объекты типа `User`.

---

Если открыть элемент массива...

```ts
response.data[0]
```

то редактор знает, что здесь находится

```ts
User
```

А значит, спокойно позволяет обращаться к полям

```ts
response.data[0].id
```

и

```ts
response.data[0].name
```

с полным автодополнением.

---

А теперь представим, что завтра сервер начнёт возвращать товары.

Нам вообще не придётся переписывать тип ответа.

Достаточно заменить параметр типа.

Например,

```ts
type Product = {
  id: number;
  title: string;
  price: number;
};
```

И использовать

```ts
ApiResponse<Product[]>
```

Контейнер остался тем же самым.

Изменилось только содержимое.

---

Именно в этом и заключается главная идея generic-типов.

Мы один раз описываем общую структуру.

А конкретный тип данных передаётся позже.

При этом TypeScript не теряет никакой информации о содержимом.

---

Обратите внимание, что в примере используется конструкция

```ts
type ApiResponse<T>
```

Но точно так же можно объявлять и generic-интерфейсы.

Например:

```ts
interface Repository<T> {
  getAll(): T[];
  save(item: T): void;
}
```

Принцип работы абсолютно такой же.

Разница лишь в том, что здесь используется `interface`, а не `type`.

---

Именно поэтому в библиотеках TypeScript очень часто встречаются конструкции вроде:

```ts
Promise<T>
```

```ts
Array<T>
```

```ts
Map<K, V>
```

```ts
Set<T>
```

Все они построены по той же самой идее.

Есть один универсальный контейнер.

И есть параметр типа, который определяет, какие именно данные этот контейнер хранит.

Благодаря этому один и тот же тип можно многократно использовать в самых разных ситуациях, не теряя точную информацию о содержимом.


## 8. Значения по умолчанию

Продолжаем ту же идею с универсальными контейнерами. В предыдущем вопросе мы передавали тип данных явно. Теперь посмотрим, как задать для одного из параметров типа стандартный вариант, чтобы не повторять его при каждом использовании.

# 8. Значения по умолчанию

В предыдущем вопросе мы создали универсальный тип ответа API.

```ts
type ApiResponse<T> =
  | ApiSuccess<T>
  | ApiFailure;
```

Здесь параметр типа `T` нужно обязательно указывать.

Например:

```ts
ApiResponse<User[]>
```

Без этого TypeScript не поймёт, какие именно данные находятся внутри успешного ответа.

Но бывают ситуации, когда у generic-типа несколько параметров, и один из них почти всегда имеет одно и то же значение.

В таком случае его можно не передавать каждый раз вручную.

Для параметра типа можно задать значение по умолчанию.

---

Представим, что сервер возвращает данные постранично.

В ответе есть массив элементов и метаинформация о пагинации.

Опишем универсальный тип.

```ts
type PaginatedResponse<
  TItem,
  TMeta = {
    page: number;
    total: number;
  },
> = {
  items: TItem[];
  meta: TMeta;
};
```

На первый взгляд запись стала немного сложнее.

Но здесь всего два параметра типа.

```ts
TItem
```

отвечает за тип элементов.

А

```ts
TMeta
```

отвечает за тип метаинформации.

---

Посмотрите на второй параметр.

```ts
TMeta = {
  page: number;
  total: number;
}
```

Знак равенства означает, что для `TMeta` задан тип по умолчанию.

Если мы не передадим второй параметр, TypeScript автоматически использует этот объект.

То есть стандартная метаинформация будет выглядеть так:

```ts
{
  page: number;
  total: number;
}
```

---

Создадим страницу пользователей.

Тип `User` у нас уже есть.

```ts
type User = {
  id: number;
  name: string;
};
```

Теперь объявим новый тип.

```ts
type UserPage = PaginatedResponse<User>;
```

Обратите внимание.

Мы передали только один параметр:

```ts
User
```

Он подставляется вместо `TItem`.

А второй параметр мы не указали.

Поэтому TypeScript использует значение по умолчанию.

Фактически тип `UserPage` будет выглядеть примерно так:

```ts
type UserPage = {
  items: User[];
  meta: {
    page: number;
    total: number;
  };
};
```

---

Теперь можно создать значение этого типа.

```ts
const userPage: UserPage = {
  items: [
    {
      id: 1,
      name: "Анна",
    },
    {
      id: 2,
      name: "Борис",
    },
  ],
  meta: {
    page: 1,
    total: 2,
  },
};
```

Поле `items` содержит пользователей.

Поле `meta` содержит номер страницы и общее количество элементов.

Это стандартный вариант пагинации.

---

Но не все API используют номера страниц.

Иногда сервер возвращает курсор.

Например, строку, которую нужно передать для загрузки следующей части данных.

Опишем другой тип метаинформации.

```ts
type CursorMeta = {
  nextCursor: string | null;
};
```

Теперь используем его в качестве второго параметра.

```ts
type CursorUserPage =
  PaginatedResponse<User, CursorMeta>;
```

В этом случае TypeScript уже не применяет значение по умолчанию.

Потому что мы явно передали собственный тип.

Теперь результат будет выглядеть примерно так:

```ts
type CursorUserPage = {
  items: User[];
  meta: {
    nextCursor: string | null;
  };
};
```

---

Создадим такой объект.

```ts
const cursorUserPage: CursorUserPage = {
  items: [
    {
      id: 1,
      name: "Анна",
    },
  ],
  meta: {
    nextCursor: "users-page-2",
  },
};
```

Или, если следующей страницы больше нет:

```ts
const lastUserPage: CursorUserPage = {
  items: [
    {
      id: 3,
      name: "Мария",
    },
  ],
  meta: {
    nextCursor: null,
  },
};
```

---

Получается удобная схема.

В большинстве случаев мы пишем:

```ts
PaginatedResponse<User>
```

и используем стандартную метаинформацию.

А когда требуется специальный вариант, передаём второй параметр явно:

```ts
PaginatedResponse<User, CursorMeta>
```

---

Значения по умолчанию особенно полезны, когда у generic-типа есть основной сценарий использования и несколько более редких вариантов.

Они уменьшают количество повторяющегося кода, но сохраняют возможность переопределить тип.

---

Здесь важно запомнить правило расположения параметров.

Обязательные параметры типов должны находиться перед параметрами со значениями по умолчанию.

Правильный вариант:

```ts
type PaginatedResponse<
  TItem,
  TMeta = DefaultMeta,
> = {};
```

Сначала обязательный `TItem`.

Затем необязательный `TMeta`.

---

А вот так записать нельзя:

```ts
type Broken<
  TMeta = DefaultMeta,
  TItem,
> = {};
```

Проблема в том, что первый параметр можно пропустить, а второй — нельзя.

TypeScript не сможет понять, какое значение к какому параметру относится.

Поэтому правило такое:

```text
Сначала обязательные параметры типов.
После них — параметры со значениями по умолчанию.
```

---

Главная идея этого вопроса заключается в следующем.

Generic-параметр необязательно передавать при каждом использовании.

Если для него существует разумный стандартный тип, этот тип можно указать после знака равенства.

Тогда generic остаётся гибким, но его обычное использование становится короче и удобнее.

В следующем вопросе логично показать generic-классы или практический репозиторий, чтобы перейти от описания типов к полноценным объектам и методам.

## 9. Generic-классы

Продолжаем развивать пример с универсальными типами. До этого дженерики использовались в функциях и типах данных. Теперь перенесём ту же идею в класс и создадим универсальное хранилище, которое сможет работать с разными сущностями и разными типами идентификаторов.

До этого момента мы использовали параметры типов в функциях.

Например:

```ts
function getProperty<T, K extends keyof T>(
  object: T,
  key: K,
): T[K] {
  return object[key];
}
```

Затем мы создавали универсальные типы-контейнеры:

```ts
type ApiResponse<T> = ApiSuccess<T> | ApiFailure;
```

И типы с несколькими параметрами:

```ts
type PaginatedResponse<TItem, TMeta = DefaultMeta> = {
  items: TItem[];
  meta: TMeta;
};
```

Но параметры типов можно использовать не только в функциях, `type` и `interface`.

Дженерик может быть и у класса.

Это особенно полезно, когда класс должен хранить или обрабатывать разные типы данных, но его внутренняя логика при этом остаётся одинаковой.

---

Представим, что нам нужен репозиторий.

Репозиторий — это объект, который отвечает за хранение сущностей.

Например, товаров, пользователей или заказов.

Он должен уметь:

* сохранять сущность;
* находить её по идентификатору;
* возвращать все сохранённые сущности.

Логика во всех случаях одинакова.

Меняются только тип сущности и тип её идентификатора.

---

Сначала опишем минимальный контракт сущности.

```ts
interface Entity<TId> {
  id: TId;
}
```

Это generic-интерфейс.

Параметр `TId` определяет тип идентификатора.

Например, у одной сущности идентификатор может быть строкой:

```ts
interface User extends Entity<string> {
  name: string;
}
```

А у другой — числом:

```ts
interface Product extends Entity<number> {
  title: string;
}
```

Интерфейс `Entity` не требует какого-то одного конкретного типа `id`.

Он только говорит:

> У сущности должен быть идентификатор того типа, который будет передан вместо `TId`.

---

Теперь создадим generic-класс репозитория.

```ts
class Repository<
  TEntity extends Entity<TId>,
  TId = string,
> {
  private readonly items = new Map<TId, TEntity>();

  save(entity: TEntity): void {
    this.items.set(entity.id, entity);
  }

  findById(id: TId): TEntity | undefined {
    return this.items.get(id);
  }

  findAll(): TEntity[] {
    return [...this.items.values()];
  }
}
```

Здесь используются два параметра типа:

```ts
TEntity
```

и

```ts
TId
```

Разберём их отдельно.

---

Параметр

```ts
TId
```

описывает тип идентификатора.

По умолчанию это строка:

```ts
TId = string
```

То есть, если другой тип не указан, репозиторий будет считать, что идентификаторы являются строками.

---

Параметр

```ts
TEntity
```

описывает сущность, которая будет храниться в репозитории.

Но это не полностью свободный тип.

Для него задано ограничение:

```ts
TEntity extends Entity<TId>
```

Это означает:

> Сущность должна как минимум содержать поле `id` типа `TId`.

Благодаря этому внутри класса TypeScript точно знает, что у каждой сущности есть свойство:

```ts
entity.id
```

И тип этого свойства совпадает с типом ключа репозитория.

---

Посмотрим на внутреннее хранилище.

```ts
private readonly items = new Map<TId, TEntity>();
```

Здесь используется встроенный generic-класс `Map`.

У него два параметра типа:

```ts
Map<тип ключа, тип значения>
```

В нашем случае ключом является идентификатор:

```ts
TId
```

А значением — сущность:

```ts
TEntity
```

Получается:

```ts
Map<TId, TEntity>
```

То есть репозиторий хранит сущности по их идентификаторам.

---

Обратите внимание на модификатор:

```ts
private readonly
```

`private` запрещает обращаться к `items` снаружи класса.

А `readonly` запрещает присвоить свойству другую коллекцию.

Например, внутри класса нельзя будет написать:

```ts
this.items = new Map();
```

Но содержимое самого объекта `Map` по-прежнему можно изменять.

Поэтому вызов:

```ts
this.items.set(...)
```

полностью допустим.

`readonly` защищает ссылку на коллекцию, а не делает коллекцию неизменяемой.

---

Теперь рассмотрим метод `save`.

```ts
save(entity: TEntity): void {
  this.items.set(entity.id, entity);
}
```

Метод принимает сущность типа `TEntity`.

Благодаря ограничению

```ts
TEntity extends Entity<TId>
```

TypeScript знает, что у неё обязательно есть поле `id`.

Причём это поле имеет тип `TId`.

Поэтому его можно безопасно использовать в качестве ключа для `Map`.

---

Следующий метод ищет сущность по идентификатору.

```ts
findById(id: TId): TEntity | undefined {
  return this.items.get(id);
}
```

Параметр `id` должен иметь именно тот тип, с которым был создан репозиторий.

Если репозиторий использует числовые идентификаторы, сюда можно передавать только числа.

Если строковые — только строки.

Результатом будет:

```ts
TEntity | undefined
```

Почему здесь присутствует `undefined`?

Потому что сущности с таким идентификатором в коллекции может не оказаться.

Метод `Map.get` в этом случае возвращает `undefined`.

---

Последний метод возвращает все сущности.

```ts
findAll(): TEntity[] {
  return [...this.items.values()];
}
```

Метод

```ts
this.items.values()
```

возвращает итератор значений `Map`.

С помощью оператора расширения:

```ts
[...this.items.values()]
```

мы превращаем его в обычный массив.

Поскольку значениями в `Map` являются объекты типа `TEntity`, результат имеет тип:

```ts
TEntity[]
```

---

Теперь посмотрим, как использовать этот класс.

Создадим тип товара.

```ts
type Product = {
  id: number;
  title: string;
};
```

У товара есть числовой идентификатор.

Значит, при создании репозитория нам нужно передать два параметра типа:

```ts
const products = new Repository<Product, number>();
```

Здесь:

```text
TEntity = Product
TId = number
```

После этого весь экземпляр класса настраивается на работу именно с товарами и числовыми идентификаторами.

---

Сохраним товар.

```ts
products.save({
  id: 1,
  title: "Клавиатура",
});
```

TypeScript проверяет передаваемый объект как `Product`.

Поэтому у него должны быть:

```ts
id: number
```

и

```ts
title: string
```

Например, такой код будет ошибочным:

```ts
// @ts-expect-error: отсутствует title
products.save({
  id: 2,
});
```

Не подойдёт и объект с неправильным типом идентификатора:

```ts
products.save({
  // @ts-expect-error: id должен быть number
  id: "3",
  title: "Мышь",
});
```

---

Теперь найдём товар.

```ts
const product = products.findById(1);
```

На месте результата TypeScript выводит:

```ts
Product | undefined
```

Поэтому перед обращением к свойствам нужно учитывать возможное отсутствие товара.

Например:

```ts
if (product) {
  console.log(product.title);
}
```

Или использовать optional chaining:

```ts
console.log(product?.title);
```

---

А теперь передадим строку вместо числа.

```ts
// @ts-expect-error: репозиторий ожидает числовой ID
products.findById("1");
```

TypeScript покажет ошибку ещё до запуска программы.

Хотя строка `"1"` и число `1` внешне похожи, это разные значения и разные типы.

Наш репозиторий был создан с параметром:

```ts
TId = number
```

Поэтому метод `findById` принимает только число.

---

Метод `findAll` также сохраняет точный тип сущности.

```ts
const allProducts = products.findAll();
```

Результатом будет:

```ts
Product[]
```

Мы можем перебрать товары и получить полноценное автодополнение.

```ts
allProducts.forEach((product) => {
  console.log(product.id);
  console.log(product.title);
});
```

TypeScript точно знает структуру каждого элемента.

---

Создадим ещё один репозиторий, но уже для пользователей со строковыми идентификаторами.

```ts
type User = {
  id: string;
  name: string;
};

const users = new Repository<User>();
```

Второй параметр мы не указали.

Поэтому используется значение по умолчанию:

```ts
TId = string
```

Теперь можно сохранить пользователя:

```ts
users.save({
  id: "user-1",
  name: "Анна",
});
```

И найти его по строковому идентификатору:

```ts
const user = users.findById("user-1");
```

А число уже не подойдёт:

```ts
// @ts-expect-error: репозиторий ожидает строковый ID
users.findById(1);
```

---

Обратите внимание, что класс `Repository` мы написали только один раз.

Но на его основе получили разные специализированные хранилища:

```ts
Repository<Product, number>
```

и

```ts
Repository<User, string>
```

Каждое из них имеет одинаковые методы.

Но методы работают со своими типами данных.

Репозиторий товаров не позволит сохранить пользователя.

```ts
const user = {
  id: "user-1",
  name: "Анна",
};

// @ts-expect-error: ожидается Product
products.save(user);
```

И репозиторий пользователей не примет товар.

Именно так дженерики не позволяют случайно смешивать данные разных сущностей.

---

Здесь параметры типов связывают сразу несколько частей класса:

```ts
TEntity
```

связывает:

* параметр метода `save`;
* значения внутри `Map`;
* результат `findById`;
* массив, возвращаемый `findAll`.

А

```ts
TId
```

связывает:

* поле `id` у сущности;
* ключ внутри `Map`;
* параметр метода `findById`.

---

Главная мысль этого вопроса заключается в следующем.

Generic-класс — это не класс, который хранит что угодно без проверки.

Это шаблон класса, для которого конкретные типы выбираются при создании экземпляра.

После этого TypeScript последовательно использует выбранные типы во всех свойствах и методах класса.

Один класс работает с разными сущностями, но каждый конкретный экземпляр остаётся строго типизированным.

## 10. Фабрика типизированных обработчиков

Продолжаем развивать generic-классы. В предыдущем вопросе параметры типов связывали сущность с идентификатором. Теперь построим более сложный пример: шина событий, где **название события определяет тип его данных**.

# 10. Фабрика типизированных обработчиков

В предыдущем вопросе мы создали generic-класс `Repository`.

В нём параметры типов связывали несколько частей класса:

```ts
TEntity
```

определял тип сохраняемой сущности, а

```ts
TId
```

определял тип её идентификатора.

Теперь рассмотрим более сложную связь.

Представим, что в приложении есть события.

Например:

```text
Пользователь создан.
Заказ оплачен.
```

У каждого события есть собственные данные.

Когда пользователь создан, нам нужны идентификатор пользователя и его имя.

Когда заказ оплачен, нам нужны идентификатор заказа и сумма платежа.

Наша задача — создать систему, в которой TypeScript будет связывать название события с правильным типом данных.

---

## Карта событий

Сначала опишем все события приложения в одном типе.

```ts
type EventMap = {
  userCreated: {
    userId: number;
    name: string;
  };
  orderPaid: {
    orderId: number;
    amount: number;
  };
};
```

Этот объект не создаётся во время выполнения программы.

Это только типовая карта.

В ней ключ — название события:

```ts
"userCreated"
```

или

```ts
"orderPaid"
```

А значение — структура данных, которая должна передаваться вместе с этим событием.

Для события `userCreated` требуется такой объект:

```ts
{
  userId: number;
  name: string;
}
```

Для события `orderPaid` — другой:

```ts
{
  orderId: number;
  amount: number;
}
```

---

Можно воспринимать `EventMap` как таблицу соответствий.

```text
userCreated → данные пользователя
orderPaid   → данные платежа
```

Именно эту связь мы хотим сохранить в методах будущего класса.

---

## Объявление класса

Создадим generic-класс `EventBus`.

```ts
class EventBus<TEvents extends object> {
  // ...
}
```

Параметр типа

```ts
TEvents
```

будет содержать карту событий.

Ограничение

```ts
TEvents extends object
```

говорит, что в качестве карты должен быть передан объектный тип.

Например:

```ts
EventBus<EventMap>
```

---

## Что должна уметь шина событий

У класса будет два основных метода.

Метод `on` регистрирует обработчик события.

Например:

```ts
bus.on("orderPaid", handler);
```

Метод `emit` запускает событие и передаёт данные всем зарегистрированным обработчикам.

```ts
bus.emit("orderPaid", {
  orderId: 10,
  amount: 5000,
});
```

Самое важное требование заключается в следующем:

если выбрано событие `"orderPaid"`, обработчик и метод `emit` должны работать только с данными платежа.

Если выбрано `"userCreated"`, они должны работать только с данными пользователя.

---

## Внутреннее хранилище

Сначала создадим коллекцию обработчиков.

```ts
private readonly handlers = new Map<
  keyof TEvents,
  Array<(payload: never) => void>
>();
```

Эта запись выглядит непривычно, поэтому разберём её по частям.

У `Map` есть два параметра типа:

```ts
Map<тип ключа, тип значения>
```

В качестве ключа мы используем:

```ts
keyof TEvents
```

Это объединение всех названий событий.

Для `EventMap` получится:

```ts
"userCreated" | "orderPaid"
```

Значением будет массив функций-обработчиков:

```ts
Array<(payload: never) => void>
```

Именно эта часть может вызвать вопрос.

Почему используется `never`, если обработчикам на самом деле нужны реальные данные?

---

## Проблема неоднородного хранилища

Посмотрим, какие обработчики мы хотим хранить.

Для события `userCreated` функция должна иметь такой тип:

```ts
(payload: {
  userId: number;
  name: string;
}) => void
```

Для события `orderPaid` — уже другой:

```ts
(payload: {
  orderId: number;
  amount: number;
}) => void
```

Получается, что внутри одной коллекции находятся функции с разными типами параметров.

Один массив предназначен для обработчиков пользователей.

Другой — для обработчиков платежей.

Но общий тип `Map` должен описать все значения одной записью.

Это и есть проблема неоднородного внутреннего хранилища.

---

Публичный API класса может точно сохранять связь между событием и обработчиком.

Но при помещении функций во внутреннюю общую коллекцию TypeScript уже не способен полностью выразить эту зависимость.

Поэтому внутри реализации нам понадобится небольшая локальная адаптация типов.

Важно, что она будет находиться только внутри класса.

Пользователь класса не сможет обойти типовые проверки.

---

## Метод `on`

Добавим метод регистрации обработчика.

```ts
on<K extends keyof TEvents>(
  event: K,
  handler: (payload: TEvents[K]) => void,
): void {
  const eventHandlers =
    this.handlers.get(event) ?? [];

  eventHandlers.push(
    handler as (payload: never) => void,
  );

  this.handlers.set(event, eventHandlers);
}
```

Здесь используется уже знакомая конструкция:

```ts
K extends keyof TEvents
```

Параметр `K` может быть только одним из ключей карты событий.

Для `EventMap` это:

```ts
"userCreated" | "orderPaid"
```

---

Первый аргумент метода:

```ts
event: K
```

определяет конкретное событие.

Второй аргумент:

```ts
handler: (payload: TEvents[K]) => void
```

зависит от выбранного события.

Если `K` равен `"orderPaid"`, TypeScript вычисляет:

```ts
TEvents["orderPaid"]
```

И получает:

```ts
{
  orderId: number;
  amount: number;
}
```

Следовательно, обработчик автоматически получает именно такой `payload`.

---

Рассмотрим тело метода.

```ts
const eventHandlers =
  this.handlers.get(event) ?? [];
```

Сначала мы пытаемся получить уже зарегистрированные обработчики события.

Если такого массива пока нет, используем пустой:

```ts
[]
```

---

Затем добавляем новый обработчик.

```ts
eventHandlers.push(
  handler as (payload: never) => void,
);
```

Здесь находится локальное утверждение типа.

Снаружи `handler` строго типизирован:

```ts
(payload: TEvents[K]) => void
```

Но внутреннее хранилище использует единый технический тип:

```ts
(payload: never) => void
```

Поэтому перед сохранением мы адаптируем функцию к внутреннему представлению.

---

После этого сохраняем массив обратно в `Map`.

```ts
this.handlers.set(event, eventHandlers);
```

Ключом остаётся конкретное событие.

Поэтому обработчик будет извлечён только при запуске того же события.

Это и есть внутренний инвариант класса.

Обработчик, зарегистрированный для `"orderPaid"`, хранится под ключом `"orderPaid"`.

Обработчик `"userCreated"` — под ключом `"userCreated"`.

---

## Метод `emit`

Теперь создадим метод запуска события.

```ts
emit<K extends keyof TEvents>(
  event: K,
  payload: TEvents[K],
): void {
  const eventHandlers =
    this.handlers.get(event) ?? [];

  for (const handler of eventHandlers) {
    handler(payload as never);
  }
}
```

Здесь используется та же связь.

```ts
event: K
```

определяет событие.

```ts
payload: TEvents[K]
```

определяет допустимые данные.

---

Если вызывается:

```ts
emit("orderPaid", ...)
```

то `K` становится равным:

```ts
"orderPaid"
```

А тип `payload` превращается в:

```ts
TEvents["orderPaid"]
```

То есть в:

```ts
{
  orderId: number;
  amount: number;
}
```

---

Внутри метода мы находим обработчики по тому же ключу.

```ts
const eventHandlers =
  this.handlers.get(event) ?? [];
```

Затем вызываем каждый из них.

```ts
for (const handler of eventHandlers) {
  handler(payload as never);
}
```

Здесь снова используется локальная адаптация.

Внутреннее хранилище описывает функцию через технический параметр `never`, поэтому и передаваемое значение адаптируется к этому типу.

Эти два утверждения типов работают парой:

```ts
handler as (payload: never) => void
```

при сохранении обработчика и

```ts
payload as never
```

при его вызове.

---

## Полный класс

Соберём код вместе.

```ts
type EventMap = {
  userCreated: {
    userId: number;
    name: string;
  };
  orderPaid: {
    orderId: number;
    amount: number;
  };
};

class EventBus<TEvents extends object> {
  private readonly handlers = new Map<
    keyof TEvents,
    Array<(payload: never) => void>
  >();

  on<K extends keyof TEvents>(
    event: K,
    handler: (payload: TEvents[K]) => void,
  ): void {
    const eventHandlers =
      this.handlers.get(event) ?? [];

    eventHandlers.push(
      handler as (payload: never) => void,
    );

    this.handlers.set(event, eventHandlers);
  }

  emit<K extends keyof TEvents>(
    event: K,
    payload: TEvents[K],
  ): void {
    const eventHandlers =
      this.handlers.get(event) ?? [];

    for (const handler of eventHandlers) {
      handler(payload as never);
    }
  }
}
```

---

## Создание типизированной шины

Теперь создадим экземпляр класса.

```ts
const bus = new EventBus<EventMap>();
```

С этого момента `bus` знает все допустимые события и соответствующие им данные.

TypeScript фактически видит такую карту:

```text
userCreated → { userId: number; name: string }
orderPaid   → { orderId: number; amount: number }
```

---

## Регистрация обработчика

Зарегистрируем обработчик оплаты заказа.

```ts
bus.on("orderPaid", (payload) => {
  console.log(payload.amount);
});
```

Обратите внимание: мы не указывали тип `payload` вручную.

TypeScript вывел его из названия события.

Поскольку первым аргументом передано:

```ts
"orderPaid"
```

тип параметра автоматически становится таким:

```ts
{
  orderId: number;
  amount: number;
}
```

Поэтому внутри обработчика доступны:

```ts
payload.orderId
```

и

```ts
payload.amount
```

---

При этом свойства другого события недоступны.

Например:

```ts
bus.on("orderPaid", (payload) => {
  console.log(payload.amount);

  // @ts-expect-error: у данных платежа нет name
  console.log(payload.name);
});
```

TypeScript понимает, что `name` относится к событию `userCreated`, а не к `orderPaid`.

---

Зарегистрируем обработчик создания пользователя.

```ts
bus.on("userCreated", (payload) => {
  console.log(
    `Создан пользователь ${payload.name}`,
  );
});
```

Теперь `payload` имеет совершенно другой тип:

```ts
{
  userId: number;
  name: string;
}
```

Один и тот же метод `on` работает с разными обработчиками, но не смешивает их данные.

---

## Запуск события

Теперь отправим событие оплаты.

```ts
bus.emit("orderPaid", {
  orderId: 10,
  amount: 5000,
});
```

TypeScript видит ключ `"orderPaid"` и требует соответствующий объект.

Оба обязательных свойства присутствуют:

```ts
orderId
```

и

```ts
amount
```

Поэтому вызов корректен.

После запуска все обработчики, зарегистрированные для `"orderPaid"`, получат этот объект.

---

Запустим событие создания пользователя.

```ts
bus.emit("userCreated", {
  userId: 1,
  name: "Анна",
});
```

Теперь TypeScript ожидает уже другую структуру.

Это тоже корректный вызов.

---

## Ошибка при неправильном `payload`

Попробуем запустить `"orderPaid"`, но передать данные пользователя.

```ts
// @ts-expect-error: payload другого события
bus.emit("orderPaid", {
  userId: 1,
  name: "Анна",
});
```

TypeScript покажет ошибку.

Для события `"orderPaid"` ожидаются:

```ts
{
  orderId: number;
  amount: number;
}
```

Но мы передали:

```ts
{
  userId: number;
  name: string;
}
```

Название события и объект данных не соответствуют друг другу.

Именно от этой ошибки нас защищает generic-связь:

```ts
event: K
payload: TEvents[K]
```

---

Нельзя передать и неизвестное событие.

```ts
// @ts-expect-error: события нет в EventMap
bus.emit("productDeleted", {
  productId: 1,
});
```

Ключ `"productDeleted"` не входит в:

```ts
keyof EventMap
```

Поэтому вызов запрещён.

---

## Почему здесь нельзя просто использовать `any`

Можно было бы объявить обработчики так:

```ts
private readonly handlers =
  new Map<string, Array<(payload: any) => void>>();
```

Но тогда публичные методы тоже легко потеряли бы связь между событием и данными.

Например, функция могла бы принять неправильный объект, а TypeScript ничего бы не сообщил.

Наша версия сохраняет строгий внешний контракт.

Пользователь класса видит точные типы:

```ts
on<K extends keyof TEvents>(
  event: K,
  handler: (payload: TEvents[K]) => void,
): void
```

и

```ts
emit<K extends keyof TEvents>(
  event: K,
  payload: TEvents[K],
): void
```

---

## Почему утверждение типа допустимо

Обычно утверждения типов стоит использовать осторожно.

Запись через `as` говорит компилятору:

> Доверься мне, я знаю об этом значении больше, чем ты можешь вывести самостоятельно.

Если использовать её без оснований, можно скрыть настоящую ошибку.

Но в нашем примере утверждение локализовано внутри класса.

Оно не доступно пользователю `EventBus`.

---

Публичный API проверяет:

* существует ли событие;
* соответствует ли обработчик выбранному событию;
* соответствует ли `payload` выбранному событию.

Внутри класса поддерживается инвариант:

```text
обработчик сохраняется под тем же ключом,
по которому затем извлекается и вызывается
```

Только методы `on` и `emit` имеют доступ к хранилищу.

Свойство `handlers` объявлено как `private`.

Поэтому посторонний код не может самостоятельно положить обработчик под неправильный ключ.

---

Именно в такой ситуации локальное утверждение типа может быть оправдано.

Не потому, что типизация мешает и её хочется отключить.

А потому, что публичный контракт уже строго проверен, а зависимость внутри неоднородного хранилища сложно полностью выразить средствами TypeScript.

---

## Где здесь фабрика

В заголовке вопроса говорится о фабрике типизированных обработчиков.

Роль фабрики здесь фактически выполняет создание специализированного экземпляра:

```ts
const bus = new EventBus<EventMap>();
```

Generic-класс `EventBus` является общим шаблоном.

А после передачи `EventMap` мы получаем конкретную типизированную шину событий.

Она уже знает:

* какие события существуют;
* какие данные принимает каждое событие;
* какой тип получает каждый обработчик.

Один класс может породить разные специализированные варианты.

Например:

```ts
type NotificationEvents = {
  emailSent: {
    email: string;
  };
  smsSent: {
    phone: string;
  };
};

const notificationBus =
  new EventBus<NotificationEvents>();
```

У этого экземпляра будет собственный набор событий и собственные типы данных.

---

## Главная идея

В этом примере дженерики связывают сразу несколько позиций.

```ts
K extends keyof TEvents
```

ограничивает название события существующими ключами.

```ts
TEvents[K]
```

получает тип данных конкретного события.

В методе `on` эта конструкция определяет тип параметра обработчика.

```ts
handler: (payload: TEvents[K]) => void
```

В методе `emit` она определяет тип отправляемых данных.

```ts
payload: TEvents[K]
```

Поэтому название события, обработчик и передаваемые данные всегда согласованы между собой.

---

Запомните основную мысль этого вопроса:

```text
Иногда внутренняя реализация требует локальной
адаптации типов, но публичный API должен оставаться
строго типизированным.
```

Утверждение типа может быть оправдано на границе реализации, если:

* внешний контракт полностью проверяется;
* утверждение находится в одном контролируемом месте;
* внутренний инвариант поддерживается самим классом;
* небезопасная деталь не выходит в публичный API.

Именно так дженерики позволяют создавать сложные, но удобные контракты, в которых один выбранный ключ автоматически определяет все связанные с ним типы.

Название раздела можно сделать точнее: **«Типизированная шина событий»** или **«Связанные события и обработчики»**, поскольку основной пример демонстрирует `EventBus`, а не отдельную фабричную функцию.

## 11. Плохие дженерики

За последние несколько вопросов мы написали довольно много дженериков.

Функции.

Типы.

Интерфейсы.

Классы.

Во всех примерах прослеживалась одна и та же идея.

Параметры типов связывали разные части программы.

Например:

тип массива и тип результата;

ключ объекта и тип значения;

название события и структуру `payload`;

тип сущности и тип её идентификатора.

Именно эта связь делала дженерики полезными.

Но теперь возникает другой вопрос.

Можно ли поставить параметр типа вообще куда угодно?

Технически — да.

Практически — не стоит.

Рассмотрим несколько распространённых ошибок.

---

## Ошибка №1. Параметр типа используется один раз

Посмотрите на такую функцию.

```ts
function parse<T>(text: string): T {
  return JSON.parse(text) as T;
}
```

На первый взгляд кажется, что она стала универсальной.

Можно получить любой тип.

Например,

```ts
const user = parse<User>(json);
```

или

```ts
const product = parse<Product>(json);
```

Выглядит красиво.

Но давайте зададим себе простой вопрос.

Откуда функция знает, что находится внутри строки?

Ответ — никак.

Она получает обычный текст.

```ts
text: string
```

Никакой связи между строкой и параметром типа `T` не существует.

---

Получается странная ситуация.

Вызывающий код может заказать абсолютно любой результат.

Например,

```ts
const productFromNothing =
  parse<Product>("null");
```

Этот код прекрасно компилируется.

Хотя строка

```ts
"null"
```

никак не может превратиться в объект `Product`.

---

Что же произошло?

На самом деле здесь дженерика почти нет.

Есть только утверждение типа.

Вот эта строка:

```ts
return JSON.parse(text) as T;
```

говорит компилятору:

> Поверь мне, здесь находится объект типа `T`.

Но никаких доказательств этому нет.

Получается обычное утверждение типа, замаскированное под красивый generic.

---

Что сделать правильно?

Самый безопасный вариант — вернуть

```ts
unknown
```

```ts
function parse(text: string): unknown {
  return JSON.parse(text);
}
```

После этого вызывающий код должен самостоятельно проверить структуру данных.

Именно так работают безопасные API.

Они не обещают того, чего не могут гарантировать.

---

## Ошибка №2. Бесполезное ограничение

Рассмотрим ещё один пример.

```ts
function length<
  T extends { length: number }
>(value: T): number {
  return value.length;
}
```

Выглядит вполне серьёзно.

Есть ограничение.

Есть параметр типа.

Но давайте посмотрим внимательнее.

Используется ли где-нибудь сам тип `T`?

Нет.

Мы только читаем свойство

```ts
length
```

И возвращаем обычное число.

---

Получается, что функция вообще не сохраняет никакой связи между типами.

Ей совершенно безразлично,

строка это,

массив,

или любой другой объект.

Важно лишь одно.

Чтобы существовало свойство

```ts
length
```

---

Поэтому дженерик здесь вообще не нужен.

Гораздо проще написать обычную функцию.

```ts
function simpleLength(
  value: { length: number },
): number {
  return value.length;
}
```

Она делает абсолютно то же самое.

Но читается значительно легче.

---

Когда параметр типа действительно нужен?

Когда он используется хотя бы в двух связанных местах.

Например,

входной параметр и результат.

Или несколько аргументов функции.

Или объект и его ключ.

Если же параметр появился один раз и ничего не связывает —

скорее всего, он лишний.

---

## Ошибка №3. Слишком много параметров типов

Иногда можно встретить примерно такие объявления.

```ts
function process<
  T,
  U,
  V,
  W,
  X,
  Y,
  Z
>(...)
```

Или ещё длиннее.

Формально всё может быть корректно.

Но возникает другой вопрос.

Поймёт ли такой API следующий разработчик?

---

Большое количество параметров типов часто говорит о том,

что модель стала слишком сложной.

Возможно,

функция выполняет слишком много обязанностей.

Или часть параметров стоит объединить в отдельный тип.

Или дать им более понятные названия.

---

Например,

вместо длинной записи

```ts
<TInput, TOutput, TError, TContext>
```

иногда лучше создать отдельный интерфейс,

который объединяет часть связанных данных.

После этого сигнатура станет значительно проще.

---

Количество параметров само по себе не является ошибкой.

В предыдущем уроке мы видели,

что `Map<K, V>` совершенно естественно использует два параметра.

А некоторые библиотеки используют три или четыре.

Главный вопрос всегда один.

Каждый ли параметр действительно описывает собственную связь?

Если да —

он оправдан.

Если нет —

скорее всего, его можно убрать.

---

## Главное правило

За весь урок мы постоянно повторяли одну мысль.

Дженерик существует не для универсальности.

И не для того, чтобы писать загадочные буквы вроде `T`, `K` и `V`.

Его задача — сохранить связь между типами.

Если параметр типа не создаёт такой связи,

значит, он, скорее всего, не нужен.

---

Поэтому перед тем как добавить новый generic, полезно задать себе три вопроса.

Первый.

Связывает ли этот параметр хотя бы два места в программе?

Второй.

Можно ли заменить его обычным типом без потери информации?

И третий.

Делает ли он API понятнее, а не сложнее?

Если ответы на эти вопросы положительные —

дженерик действительно приносит пользу.

Если нет —

скорее всего, перед вами пример плохого использования generic.

Именно поэтому опытные разработчики стремятся не к максимальному количеству параметров типов, а к максимально понятным и выразительным контрактам.

Хороший дженерик делает API точнее.

Плохой — лишь создаёт иллюзию универсальности и усложняет чтение кода.

Такой финальный раздел хорошо замыкает весь урок: вы начинаете с проблемы потери информации, затем показываете, как дженерики сохраняют связи между типами, а в конце формулируете главный критерий их применения — **используйте дженерики только там, где они действительно выражают и сохраняют эти связи**.


## Практика

Реализуйте:

```ts
class Cache<TKey, TValue> {
  // set, get, has, delete, getOrSet
}
```

Требования:

- ключ может быть любого типа, допустимого для `Map`;
- значение сохраняет свой тип;
- `get` возвращает `TValue | undefined`;
- `getOrSet` принимает фабрику `() => TValue`;
- добавьте вариант с асинхронной фабрикой.

Затем создайте `Repository<TEntity, TId>` с функцией выбора ID, а не с обязательным полем `id`.
