# Урок 12. Встроенные utility types

## 1. Исходная модель

В этом уроке мы познакомимся со встроенными utility types TypeScript.

Практически все они работают по одному принципу.

Они не создают тип с нуля, а преобразуют уже существующий.

Чтобы не придумывать новый пример для каждого utility type, будем использовать одну и ту же модель пользователя.

Создадим тип `User`.

```ts
type User = {
  readonly id: number;
  name: string;
  email: string;
  role: "admin" | "editor" | "viewer";
  avatarUrl?: string;
  readonly createdAt: Date;
};
```

Это обычный тип пользователя с несколькими обязательными полями, необязательным аватаром и двумя полями только для чтения.

Пока нас не интересует, почему некоторые свойства объявлены через `readonly`, а другие имеют знак вопроса.

Главное, что этот тип достаточно разнообразный, чтобы на нём показать работу всех основных utility types.

В следующих вопросах мы будем брать именно этот тип и получать из него новые типы без переписывания всех свойств вручную.

Поэтому запомните только одно.

Исходной моделью для всех дальнейших примеров будет тип `User`.

## 2. Partial<T>

Первый utility type, который мы рассмотрим, называется `Partial`.

Его задача очень простая.

Он делает все свойства типа необязательными.

Возьмём тип `User` из предыдущего вопроса.

Чтобы получить его частичную версию, достаточно написать:

```ts
type PartialUser = Partial<User>;
```

После этого TypeScript автоматически создаст новый тип, в котором каждое свойство станет необязательным.

Нам не пришлось перечислять поля вручную.

Внутри `Partial` устроен очень просто.

Его приблизительная реализация выглядит так:

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
```

Мы уже умеем читать такой код.

`keyof T` получает все ключи исходного типа.

Mapped type проходит по каждому ключу.

Знак вопроса делает каждое свойство необязательным.

А `T[K]` сохраняет исходный тип значения.

Именно поэтому `Partial` не меняет типы свойств.

Он меняет только их обязательность.

На практике `Partial` часто используют при постепенном заполнении объекта.

Например, при работе с черновиком формы.

```ts
function mergeDraft(
  current: Partial<User>,
  patch: Partial<User>,
): Partial<User> {
  return { ...current, ...patch };
}
```

В этой функции оба объекта могут содержать только часть свойств пользователя.

Мы объединяем их и получаем новый черновик.

Это хороший пример использования `Partial`.

Но теперь рассмотрим другую ситуацию.

Предположим, нам нужно описать команду обновления пользователя.

Иногда возникает желание просто написать `Partial<User>`.

Однако это будет не совсем правильно.

```ts
type UpdateUserCommand = {
  userId: number;
  name?: string;
  email?: string;
  avatarUrl?: string | null;
};
```

Во время обновления мы не должны разрешать изменение `id` или `createdAt`.

Кроме того, для поиска пользователя нужен отдельный `userId`.

Поэтому команда обновления имеет собственный смысл и собственную структуру.

Получается важное правило.

`Partial` отлично подходит для технических задач, например хранения черновиков.

Но если вы описываете предметную команду, сначала подумайте о её смысле, а уже потом решайте, нужен ли здесь utility type.

## 3. Required<T>

Следующий utility type называется `Required`.

Он выполняет действие, противоположное `Partial`.

Если `Partial` делает все свойства необязательными, то `Required` делает все свойства обязательными.

Возьмём наш тип `User`.

```ts
type CompleteUser = Required<User>;
```

После такого преобразования все свойства становятся обязательными.

Например, свойство `avatarUrl` больше нельзя пропускать.

При создании объекта его уже придётся указать.

Внутри `Required` устроен почти так же, как `Partial`.

Его упрощённая реализация выглядит следующим образом.

```ts
type MyRequired<T> = {
  [K in keyof T]-?: T[K];
};
```

Здесь используется уже знакомый mapped type.

Главное отличие — запись `-?`.

Она убирает признак необязательного свойства.

Все остальные части остаются такими же.

Важно понимать одну особенность `Required`.

Он делает свойство обязательным, но не изменяет его тип.

Рассмотрим пример.

```ts
type Example = {
  value?: string | undefined;
};

type CompleteExample = Required<Example>;
// value: string | undefined
```

После применения `Required` свойство `value` действительно становится обязательным.

Но его тип остаётся прежним.

То есть значение всё ещё может быть равно `undefined`, потому что `undefined` явно входит в состав типа.

Поэтому `Required` влияет только на обязательность свойства.

Он не изменяет тип значения этого свойства.

## 4. Readonly<T>

Следующий utility type называется `Readonly`.

Он делает все свойства типа доступными только для чтения.

Возьмём тип `User`.

```ts
type ReadonlyUser = Readonly<User>;
```

После такого преобразования каждое свойство становится `readonly`.

Изменять их больше нельзя.

Внутри `Readonly` реализован очень просто.

```ts
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};
```

Как и раньше, mapped type проходит по всем ключам исходного типа.

Но теперь перед каждым свойством добавляется модификатор `readonly`.

В результате все свойства нового типа становятся доступными только для чтения.

Однако здесь есть важная особенность.

`Readonly` выполняет только поверхностное преобразование.

Он защищает лишь свойства верхнего уровня.

Если внутри объекта находятся другие объекты или массивы, они не становятся автоматически неизменяемыми.

Для их защиты потребуются другие решения.

Поэтому `Readonly` делает неизменяемыми только свойства самого объекта, к которому он применяется.

## 5. Pick<T, K>

Следующий utility type называется `Pick`.

Он позволяет выбрать только определённые свойства существующего типа.

Например, для списка пользователей нам могут понадобиться только идентификатор, имя и роль.

В этом случае можно написать:

```ts
type UserListItem = Pick<User, "id" | "name" | "role">;
```

В результате получится новый тип, содержащий только эти три свойства.

Все остальные свойства будут исключены.

Внутри `Pick` реализован следующим образом.

```ts
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};
```

Первый параметр — это исходный тип.

Второй параметр — набор ключей, которые нужно оставить.

`K extends keyof T` гарантирует, что можно выбирать только существующие свойства.

Затем mapped type проходит по этим ключам и переносит их в новый тип вместе с исходными типами значений.

`Pick` удобно использовать, когда новый тип действительно является частью существующей модели.

Но так бывает не всегда.

Например, если карточка пользователя содержит вычисляемые поля, лучше описать её явно.

```ts
type UserCard = {
  id: number;
  displayName: string;
  roleLabel: string;
};
```

Здесь `displayName` и `roleLabel` не существуют в типе `User`.

Они появляются в результате обработки данных.

Поэтому в такой ситуации лучше создать отдельный тип с понятным названием, чем пытаться получить его с помощью `Pick`.

## 6. Omit<T, K>

Следующий utility type называется `Omit`.

Он работает противоположным образом по сравнению с `Pick`.

Если `Pick` выбирает нужные свойства, то `Omit` исключает указанные свойства.

Например, при создании нового пользователя идентификатор и дата создания ещё неизвестны.

Можно описать такой тип следующим образом.

```ts
type NewUser = Omit<User, "id" | "createdAt">;
```

В результате получится новый тип, содержащий все свойства `User`, кроме `id` и `createdAt`.

Внутри `Omit` реализован довольно просто.

```ts
type MyOmit<T, K extends PropertyKey> = Pick<T, Exclude<keyof T, K>>;
```

Сначала `Exclude` получает все ключи исходного типа и исключает из них указанные.

Затем `Pick` создаёт новый тип только из оставшихся ключей.

Получается, что `Omit` построен на уже известных нам utility types.

`Omit` хорошо подходит, когда нужно исключить небольшое количество свойств.

Если же исключать приходится почти все поля, а оставить лишь несколько, такой код становится менее понятным.

В подобных случаях обычно лучше использовать `Pick`, потому что он сразу показывает, какие свойства должны остаться.

## 7. Record<K, V>

Следующий utility type называется `Record`.

Он создаёт объектный тип, в котором заранее известен набор ключей и тип их значений.

Сначала получим тип ролей пользователя.

```ts id="z5f0v1"
type Role = User["role"];
```

Теперь создадим объект, который содержит подпись для каждой роли.

```ts id="fjlwmx"
const roleLabels: Record<Role, string> = {
  admin: "Администратор",
  editor: "Редактор",
  viewer: "Наблюдатель",
};
```

Здесь `Role` задаёт все возможные ключи объекта.

А `string` означает, что значением каждого ключа должна быть строка.

Получается, что TypeScript заранее знает полный набор допустимых ключей.

Если позже в тип `Role` будет добавлена новая роль, компилятор сразу сообщит об ошибке и потребует добавить для неё подпись.

Благодаря этому `Record` удобно использовать для создания исчерпывающих словарей.

Внутри он реализован очень просто.

```ts id="m2w3py"
type MyRecord<K extends PropertyKey, V> = {
  [P in K]: V;
};
```

Mapped type проходит по всем ключам из `K` и создаёт свойство с типом значения `V`.

Иногда требуется описать словарь, в котором могут присутствовать не все ключи.

Для этого можно объединить `Record` с уже знакомым `Partial`.

```ts id="7w2t7o"
type OptionalRoleLabels = Partial<Record<Role, string>>;
```

Теперь каждый ключ становится необязательным.

Такой тип подходит для частично заполненных словарей.

## 8. Exclude, Extract, NonNullable

Следующие utility types предназначены для работы с объединениями типов.

Начнём с `Exclude`.

Предположим, у нас есть тип со статусами заказа.

```ts id="2y7vfk"
type Status = "draft" | "pending" | "paid" | "cancelled";

type ActiveStatus = Exclude<Status, "cancelled">;
```

`Exclude<T, U>` удаляет из объединения все варианты, которые совместимы с типом `U`.

В результате тип `ActiveStatus` будет содержать все статусы, кроме `"cancelled"`.

Следующий utility type — `Extract`.

Он работает противоположным образом.

```ts id="0cxjnh"
type TerminalStatus = Extract<Status, "paid" | "cancelled">;
```

`Extract` оставляет только те варианты, которые входят в указанное объединение.

В результате тип `TerminalStatus` будет содержать только `"paid"` и `"cancelled"`.

Теперь рассмотрим `NonNullable`.

```ts id="xgp4tt"
type MaybeUser = User | null | undefined;
type ExistingUser = NonNullable<MaybeUser>;
// User
```

`NonNullable` удаляет из объединения значения `null` и `undefined`.

В результате остаётся только тип `User`.

Все три utility type основаны на conditional types.

Их упрощённые реализации выглядят следующим образом.

```ts id="tbifzs"
type MyExclude<T, U> = T extends U ? never : T;
type MyExtract<T, U> = T extends U ? T : never;
type MyNonNullable<T> = T extends null | undefined ? never : T;
```

Здесь используется уже знакомый нам conditional type.

Поскольку он распределяется по объединению, TypeScript проверяет каждый элемент union отдельно.

Именно благодаря этому `Exclude`, `Extract` и `NonNullable` могут независимо обработать каждый вариант объединения.

## 9. Типы функций

Utility types умеют работать не только с объектами, но и с функциями.

Рассмотрим пример.

```ts id="zl4sxm"
function createOrder(userId: number, productIds: number[]) {
  return {
    id: crypto.randomUUID(),
    userId,
    productIds,
    status: "draft" as const,
  };
}

type CreateOrderParameters = Parameters<typeof createOrder>;

type CreatedOrder = ReturnType<typeof createOrder>;
```

`Parameters` получает тип параметров функции.

В нашем случае это кортеж.

```ts id="y5w3te"
[userId: number, productIds: number[]]
```

Каждый элемент кортежа соответствует одному параметру функции.

`ReturnType` работает аналогично.

Он получает тип значения, которое возвращает функция.

Эти utility types особенно полезны, когда нужно использовать существующую сигнатуру функции, не дублируя её вручную.

Например, можно написать универсальную функцию-обёртку.

```ts id="z6by4l"
function withLogging<TArgs extends unknown[], TResult>(
  fn: (...args: TArgs) => TResult,
): (...args: TArgs) => TResult {
  return (...args) => {
    console.log("Аргументы:", args);
    const result = fn(...args);
    console.log("Результат:", result);
    return result;
  };
}

const loggedCreateOrder = withLogging(createOrder);
```

Функция `withLogging` принимает другую функцию, выводит её аргументы и результат, а затем возвращает новую функцию.

При этом типы параметров и возвращаемого значения сохраняются автоматически.

Поэтому после создания

```ts
const loggedCreateOrder = withLogging(createOrder);
```

новая функция имеет ту же сигнатуру, что и исходная `createOrder`.

Это одно из самых полезных применений utility types для работы с функциями.

## 10. Конструкторы

Utility types умеют работать не только с обычными функциями, но и с конструкторами классов.

Рассмотрим пример.

```ts id="u1r5mx"
class Product {
  constructor(
    public readonly id: number,
    public title: string,
  ) {}
}

type ProductConstructorArgs = ConstructorParameters<typeof Product>;

type ProductInstance = InstanceType<typeof Product>;
```

Здесь используются два новых utility type.

`ConstructorParameters` получает тип параметров конструктора.

В нашем примере это кортеж, содержащий типы аргументов конструктора класса `Product`.

`InstanceType` получает тип экземпляра, который создаётся этим конструктором.

Поэтому `ProductInstance` будет иметь тип `Product`.

Обратите внимание на запись

```ts id="i2s4bw"
typeof Product;
```

В типовой позиции она означает тип самого конструктора.

Именно его ожидают `ConstructorParameters` и `InstanceType`.

А запись

```ts id="0o7mki"
Product;
```

без `typeof` обозначает тип экземпляра класса.

Это важно помнить.

`typeof Product` — тип конструктора.

`Product` — тип объекта, который создаётся этим конструктором.

## 11. Awaited<T>

Последний utility type, который мы рассмотрим, — `Awaited`.

Он используется при работе с асинхронными функциями.

Рассмотрим пример.

```ts
async function loadUser(): Promise<User> {
  return {
    id: 1,
    name: "Анна",
    email: "anna@example.com",
    role: "admin",
    createdAt: new Date(),
  };
}

type LoadedUser = Awaited<ReturnType<typeof loadUser>>;
// User
```

Сначала `ReturnType` получает тип, который возвращает функция `loadUser`.

Это будет `Promise<User>`.

Затем `Awaited` извлекает из него внутренний тип.

В результате `LoadedUser` становится просто типом `User`.

Такой подход особенно удобен, когда тип результата не хочется дублировать вручную.

Достаточно получить его непосредственно из функции.

Важно, что `Awaited` умеет рекурсивно разворачивать `Promise`.

Если один `Promise` содержит другой, будет получен итоговый внутренний тип.

Кроме того, `Awaited` корректно работает с объединениями типов, поэтому его можно безопасно использовать в более сложных моделях данных.

На этом знакомство со встроенными utility types завершено.

Теперь вы знаете самые востребованные преобразования типов, которые ежедневно используются в современных проектах на TypeScript.

## 12. Собираем типы заказа

В завершение объединим несколько изученных приёмов в одном примере.

У нас есть полная модель заказа.

```ts
type Order = {
  readonly id: string;
  readonly createdAt: Date;
  userId: number;
  status: "draft" | "paid" | "cancelled";
  items: Array<{
    productId: number;
    quantity: number;
    unitPrice: number;
  }>;
};
```

Эта модель содержит все данные заказа.

Но в разных частях приложения нам понадобятся разные типы.

### Заказ в списке

В списке заказов не нужно показывать пользователя и все товары.

Оставим только идентификатор, дату и статус.

```ts
type OrderListItem =
  Pick<Order, "id" | "createdAt" | "status"> & {
    total: number;
  };
```

`Pick` выбирает три поля из `Order`.

Поле `total` добавляется отдельно, потому что в исходной модели его нет. Оно вычисляется на основе стоимости товаров.

Пример объекта:

```ts
const orderListItem: OrderListItem = {
  id: "order-1",
  createdAt: new Date(),
  status: "paid",
  total: 6500,
};
```

### Команда создания заказа

Теперь опишем данные, которые клиент передаёт при создании заказа.

```ts
type CreateOrderCommand = {
  userId: Order["userId"];
  items: Array<{
    productId: number;
    quantity: number;
  }>;
};
```

Идентификатор пользователя берём из модели `Order`.

```ts
Order["userId"]
```

Сейчас это `number`.

При этом клиент не передаёт:

* идентификатор заказа;
* дату создания;
* статус;
* цену товара.

Эти данные должна определить сама система.

Пример команды:

```ts
const createCommand: CreateOrderCommand = {
  userId: 15,
  items: [
    {
      productId: 101,
      quantity: 2,
    },
  ],
};
```

### Команда смены статуса

Для смены статуса нужны только идентификатор заказа и новый статус.

```ts
type ChangeOrderStatusCommand = {
  orderId: Order["id"];
  status: Exclude<Order["status"], "draft">;
};
```

Тип идентификатора берём из поля `id`.

```ts
Order["id"]
```

А выражение

```ts
Exclude<Order["status"], "draft">
```

удаляет `"draft"` из объединения статусов.

Поэтому остаются только:

```ts
"paid" | "cancelled"
```

Пример правильной команды:

```ts
const changeStatusCommand: ChangeOrderStatusCommand = {
  orderId: "order-1",
  status: "paid",
};
```

А передать `"draft"` уже нельзя:

```ts
const wrongCommand: ChangeOrderStatusCommand = {
  orderId: "order-1",
  status: "draft",
};
```

TypeScript покажет ошибку.

В результате из одной модели `Order` мы получили несколько типов для разных задач:

```ts
OrderListItem
CreateOrderCommand
ChangeOrderStatusCommand
```

`Pick` помогает выбрать нужные поля.

Indexed access позволяет взять тип отдельного свойства.

`Exclude` удаляет ненужный вариант из объединения.

Главное преимущество в том, что новые типы связаны с моделью `Order` и не дублируют её полностью.

## Практика

Из модели `Product` получите:

- `ProductListItem`;
- `CreateProductCommand`;
- `UpdateProductCommand`, не разрешающий менять ID;
- `PublicProduct`, исключающий внутреннюю себестоимость;
- карту статусов в подписи через `Record`;
- тип результата асинхронной `loadProducts`.

Для двух команд сравните utility-based вариант с явным объектным типом и выберите более понятный.
