# Урок 11. Вычисляем новые типы из существующих

TypeScript позволяет обращаться с типами как с данными: получать ключи, выбирать свойства, выполнять условные преобразования и строить новые имена. Эти возможности особенно полезны в библиотеках и общих инфраструктурных модулях.

## 1. keyof

В предыдущих уроках мы уже создавали собственные типы. Но TypeScript умеет делать гораздо больше.

Он может получать новую информацию из уже существующих типов.

Первый оператор, с которого мы начнём, называется `keyof`.

Посмотрим на пример.

```ts
type User = {
  id: number;
  name: string;
  active: boolean;
};
```

Здесь всё просто.

Есть тип `User` с тремя свойствами: `id`, `name` и `active`.

Теперь используем `keyof`.

```ts
type UserKey = keyof User;
```

На первый взгляд кажется, что здесь происходит что-то сложное.

На самом деле всё очень просто.

`keyof` берёт тип объекта и возвращает объединение всех его ключей.

В нашем случае получится:

```ts
"id" | "name" | "active"
```

Поскольку типы существуют только во время компиляции, вывести их через console.log нельзя. Чтобы увидеть результат работы keyof, достаточно навести курсор на тип в VS Code или попробовать присвоить значение, которого среди ключей нет. Редактор сразу покажет ошибку.

То есть `UserKey` может содержать только одно из трёх допустимых значений.

Например:

```ts
const key1: UserKey = "id";
const key2: UserKey = "name";
```

А вот так уже нельзя:

```ts
const key3: UserKey = "age";
```

Потому что свойства `age` в типе `User` нет.

Именно в этом главная идея `keyof`.

Мы больше не перечисляем ключи вручную.

TypeScript сам получает их из существующего типа.

Это особенно удобно.

Представьте, что позже мы добавим новое поле:

```ts
type User = {
  id: number;
  name: string;
  active: boolean;
  email: string;
};
```

Теперь `UserKey` автоматически станет:

```ts
"id" | "name" | "active" | "email"
```

Ничего дополнительно менять не потребуется.

Теперь посмотрим, где это действительно полезно.

Допустим, мы хотим написать функцию, которая получает объект пользователя и имя свойства, а затем возвращает значение этого свойства.

Вот такая функция.

```ts
function pickProperty<K extends UserKey>(
  user: User,
  key: K,
): User[K] {
  return user[key];
}
```

Пока не пугайтесь этой записи.

Сейчас нас интересует только `keyof`.

Параметр `key` имеет тип `UserKey`.

А значит, передать можно только существующий ключ объекта.

Например:

```ts
const user: User = {
  id: 1,
  name: "Алексей",
  active: true,
};

const value = pickProperty(user, "name");
```

Всё работает.

Но если попробовать написать:

```ts
pickProperty(user, "age");
```

TypeScript сразу сообщит об ошибке.

Потому что такого свойства не существует.

То есть `keyof` помогает сделать код безопаснее.

Теперь небольшая особенность.

До этого мы работали с обычными объектами.

Но существуют ещё объекты с индексными сигнатурами.

Например:

```ts
type Scores = {
  [id: number]: number;
};
```

Здесь ключами являются числа.

Поэтому:

```ts
type ScoreKey = keyof Scores;
```

получит тип `number`.

А если индексная сигнатура строковая:

```ts
type Dictionary = {
  [key: string]: string;
};
```

то результат будет таким:

```ts
type DictionaryKey = keyof Dictionary;
```

Тип окажется:

```ts
string | number
```

Почему появляется ещё и `number`?

Потому что в JavaScript числовые ключи объектов автоматически преобразуются в строки.

Для большинства проектов достаточно запомнить простое правило:

**`keyof` возвращает все допустимые ключи объекта.**

Именно поэтому он очень часто используется вместе с дженериками и позволяет писать функции, которые работают только с существующими свойствами объекта.

## 2. typeof в типовой позиции

В предыдущих уроках мы уже использовали оператор `typeof`.

Например:

```ts
console.log(typeof 42);
```

Результат будет таким:

```text
number
```

То есть в обычном JavaScript `typeof` работает **во время выполнения программы** и возвращает строку с названием типа значения.

Но в TypeScript существует ещё один вариант использования `typeof`.

Он работает совсем иначе.

Посмотрим на пример.

```ts
const defaultConfig = {
  locale: "ru",
  pageSize: 20,
  features: {
    recommendations: true,
  },
};
```

Допустим, мы хотим создать тип, который полностью соответствует этому объекту.

Конечно, можно написать его вручную.

```ts
type Config = {
  locale: string;
  pageSize: number;
  features: {
    recommendations: boolean;
  };
};
```

Но здесь появляется проблема.

Теперь одна и та же модель описана дважды.

Есть объект.

И есть отдельный тип.

Если позже изменить объект и забыть изменить тип, они перестанут совпадать.

Именно поэтому TypeScript позволяет получить тип автоматически.

Для этого используется `typeof` в типовой позиции.

```ts
type Config = typeof defaultConfig;
```

Здесь `typeof` уже ничего не проверяет во время выполнения.

Он просто говорит компилятору:

> «Возьми тип переменной `defaultConfig` и используй его здесь.»

В результате `Config` станет точно таким же типом, как и наш объект.

Никакого дублирования больше нет.

Это очень удобно.

Изменим объект.

Например, добавим новое свойство.

```ts
const defaultConfig = {
  locale: "ru",
  pageSize: 20,
  theme: "dark",
  features: {
    recommendations: true,
  },
};
```

Тип `Config` автоматически обновится.

Ничего менять вручную уже не потребуется.

Но здесь есть важное правило.

Не всегда стоит получать тип через `typeof`.

Если тип является самостоятельным контрактом программы, который существует независимо от конкретного объекта, его обычно лучше описать явно.

А вот если объект является источником истины, тогда `typeof` избавляет нас от дублирования.

Есть ещё одно очень популярное применение.

Посмотрите на такой массив.

```ts
const roles = ["admin", "editor", "viewer"] as const;
```

Мы уже знаем, что `as const` делает элементы литеральными и только для чтения.

Теперь получим тип массива.

```ts
typeof roles
```

Он будет примерно таким:

```ts
readonly ["admin", "editor", "viewer"]
```

Но нас интересует не весь массив, а тип любого его элемента.

Для этого используется запись:

```ts
type Role = (typeof roles)[number];
```

Она выглядит необычно, но читается довольно просто.

Сначала мы получаем тип массива с помощью `typeof`.

Затем `[number]` означает:

> «Возьми тип элемента массива.»

В результате получится:

```ts
type Role = "admin" | "editor" | "viewer";
```

Теперь можно использовать этот тип.

```ts
const role: Role = "admin";
```

А вот так уже нельзя.

```ts
const role: Role = "manager";
```

Компилятор сразу сообщит об ошибке.

Именно поэтому конструкция `(typeof array)[number]` очень часто встречается в современных TypeScript-проектах.

Она позволяет получить объединение всех значений массива автоматически, без ручного перечисления литералов.

## 3. Indexed access types

Мы уже научились получать ключи объекта с помощью `keyof`.

А теперь посмотрим, как получить **тип конкретного свойства**.

Для этого используются так называемые **Indexed Access Types**.

Звучит сложно, но идея очень простая.

Возьмём уже знакомый тип.

```ts
type User = {
  id: number;
  name: string;
  active: boolean;
};
```

Предположим, нам нужен только тип свойства `name`.

Вместо того чтобы писать его вручную, можно обратиться к нему вот так:

```ts
type UserName = User["name"];
```

В результате получится:

```ts
type UserName = string;
```

То есть запись

```ts
User["name"]
```

читается буквально так:

> «Возьми тип свойства `name` из типа `User`.»

Можно проверить это очень просто.

```ts
const name: UserName = "Алексей";
```

А вот так уже нельзя.

```ts
const name: UserName = 123;
```

Компилятор сообщит об ошибке, потому что `UserName` — это `string`.

Но можно получить сразу несколько свойств.

Например:

```ts
type UserIdentity = User["id" | "name"];
```

Что здесь происходит?

Мы передали не один ключ, а объединение ключей.

TypeScript посмотрит на оба свойства.

У `id` тип `number`.

У `name` тип `string`.

Поэтому итоговый тип будет таким:

```ts
type UserIdentity = number | string;
```

То есть если ключей несколько, результатом становится объединение типов этих свойств.

Это уже само по себе полезно.

Но чаще всего Indexed Access Types используют немного иначе.

Представим, что мы получили ответ от сервера.

```ts
type ApiResponse = {
  users: Array<{
    id: number;
    name: string;
  }>;
};
```

Внутри находится массив пользователей.

Теперь допустим, что в другом месте программы нам нужен тип **одного пользователя**.

Конечно, можно снова написать его вручную.

```ts
type ApiUser = {
  id: number;
  name: string;
};
```

Но это снова дублирование.

Если структура пользователя изменится, нам придётся исправлять её сразу в нескольких местах.

Вместо этого можно взять тип прямо из существующего контракта.

```ts
type ApiUser = ApiResponse["users"][number];
```

Разберём эту запись по частям.

Сначала:

```ts
ApiResponse["users"]
```

Это тип свойства `users`.

То есть:

```ts
Array<{
  id: number;
  name: string;
}>
```

А затем идёт ещё одна запись:

```ts
[number]
```

Она означает:

> «Возьми тип любого элемента этого массива.»

В результате получится:

```ts
type ApiUser = {
  id: number;
  name: string;
};
```

Получается, мы не описывали пользователя вручную.

Мы просто извлекли его тип из уже существующей модели.

Это очень удобно.

Если завтра сервер начнёт возвращать ещё и поле `email`, достаточно изменить только `ApiResponse`.

Тип `ApiUser` автоматически обновится.

Именно поэтому Indexed Access Types часто используются в больших проектах.

Они позволяют получать нужные типы из уже существующих моделей и не дублировать описание одной и той же структуры в разных местах программы.

Ниже простой сценарий без лишнего усложнения.

## 4. Conditional types

Теперь перейдём к условным типам.

Они позволяют TypeScript выбирать один тип или другой в зависимости от условия.

Посмотрим на простой пример.

```ts
type IsString<T> = T extends string ? true : false;
```

Эта запись похожа на тернарный оператор в JavaScript.

Только здесь мы работаем не со значениями, а с типами.

Читается она так:

> «Если тип `T` совместим со `string`, вернуть `true`. Иначе вернуть `false`.»

Проверим.

```ts
type A = IsString<"hello">;
```

Строковый литерал `"hello"` совместим с типом `string`.

Поэтому получится:

```ts
type A = true;
```

Теперь другой пример.

```ts
type B = IsString<number>;
```

Тип `number` не совместим со `string`.

Поэтому результат будет таким:

```ts
type B = false;
```

Общая форма условного типа выглядит так:

```ts
T extends SomeType ? TrueType : FalseType
```

Сначала TypeScript проверяет условие.

Если оно выполняется, выбирается тип после знака вопроса.

Если нет — тип после двоеточия.

Теперь посмотрим на более практический пример.

Допустим, нам нужно получить тип элемента массива.

Создадим условный тип:

```ts
type ArrayElement<T> =
  T extends readonly (infer TItem)[]
    ? TItem
    : never;
```

Пока эта запись может выглядеть непривычно.

Разберём её по частям.

Сначала TypeScript проверяет:

```ts
T extends readonly (infer TItem)[]
```

То есть:

> «Похож ли тип `T` на массив?»

Если да, TypeScript извлекает тип элемента массива и временно называет его `TItem`.

Затем возвращает этот тип:

```ts
? TItem
```

Если `T` не является массивом, возвращается `never`:

```ts
: never
```

Используем наш тип.

```ts
type Item = ArrayElement<string[]>;
```

Тип `string[]` — это массив строк.

Значит, TypeScript извлечёт тип его элемента.

Результат:

```ts
type Item = string;
```

Можно проверить и с другим массивом.

```ts
type NumberItem = ArrayElement<number[]>;
```

Получится:

```ts
type NumberItem = number;
```

А если передать не массив:

```ts
type WrongItem = ArrayElement<boolean>;
```

Результатом будет:

```ts
type WrongItem = never;
```

Пока достаточно запомнить простую идею.

`infer TItem` можно воспринимать как объявление переменной типа внутри условия.

Если TypeScript распознаёт подходящую структуру, он сохраняет найденный тип в `TItem`.

Итак, условные типы позволяют выбирать результат в зависимости от входного типа.

А `infer` помогает извлекать часть типа из уже известной структуры.

Следующий сценарий логично посвятить `infer` отдельно или сразу перейти к distributive conditional types.

## 5. Распределение по объединению

Мы только что познакомились с условными типами.

Но у них есть одна особенность, которая сначала может показаться неожиданной.

Посмотрите на такой пример.

```ts
type ToArray<T> = T extends unknown ? T[] : never;
```

Здесь всё выглядит довольно просто.

Если тип подходит под условие, мы превращаем его в массив.

Проверим с обычным типом.

```ts
type Numbers = ToArray<number>;
```

Получится:

```ts
type Numbers = number[];
```

Всё ожидаемо.

Теперь попробуем передать объединение типов.

```ts
type Distributed = ToArray<string | number>;
```

Как вы думаете, что получится?

Многие ожидают увидеть вот такой результат:

```ts
(string | number)[]
```

Но это неверно.

На самом деле TypeScript поступает иначе.

Он берёт каждый тип из объединения отдельно.

Сначала:

```ts
ToArray<string>
```

Получается:

```ts
string[]
```

Затем:

```ts
ToArray<number>
```

Получается:

```ts
number[]
```

После этого TypeScript объединяет результаты.

Итоговый тип будет таким:

```ts
type Distributed = string[] | number[];
```

Именно это поведение называется **распределением по объединению**.

То есть условный тип автоматически применяется к каждому элементу объединения отдельно.

Почему это происходит?

Потому что слева от `extends` находится сам параметр типа `T`.

Такой параметр называют **голым параметром типа**.

Именно в этом случае TypeScript включает распределение автоматически.

Но иногда нужно другое поведение.

Допустим, мы действительно хотим получить массив, элементы которого могут быть и строками, и числами.

То есть вот такой тип:

```ts
(string | number)[]
```

Для этого достаточно сделать небольшую хитрость.

```ts
type ToArrayTogether<T> =
  [T] extends [unknown] ? T[] : never;
```

Обратите внимание на квадратные скобки.

Мы обернули обе стороны условия в кортеж.

Теперь проверим.

```ts
type Together = ToArrayTogether<string | number>;
```

Результат будет уже другим.

```ts
type Together = (string | number)[];
```

Почему так произошло?

Потому что после добавления кортежей TypeScript больше не рассматривает каждый элемент объединения отдельно.

Он воспринимает всё объединение как один тип.

Поэтому распределение отключается.

Для этого вопроса достаточно запомнить простое правило.

Если в условном типе слева от `extends` находится **голый параметр типа**, TypeScript распределяет условие по каждому элементу объединения.

Если же обернуть обе стороны условия в кортежи:

```ts
[T] extends [unknown]
```

то распределение отключается, и всё объединение обрабатывается как единое целое.

## 6. infer

В предыдущем вопросе мы уже встретили ключевое слово `infer`.

Теперь разберём его отдельно.

`infer` позволяет извлечь часть типа и сохранить её во временную переменную типа.

Посмотрим на пример с функцией.

```ts
type FunctionResult<T> =
  T extends (...args: never[]) => infer TResult
    ? TResult
    : never;
```

Сначала эта запись может выглядеть сложно.

Но идея здесь простая.

Мы проверяем:

> «Является ли тип `T` функцией?»

Эта часть описывает любую функцию:

```ts
(...args: never[]) => infer TResult
```

Нас сейчас не интересуют её параметры.

Нас интересует только возвращаемый тип.

Поэтому после стрелки используется:

```ts
infer TResult
```

Это можно прочитать так:

> «Определи возвращаемый тип функции и назови его `TResult`.»

Если `T` действительно является функцией, условный тип возвращает `TResult`.

Если нет, возвращается `never`.

Теперь создадим обычную функцию.

```ts
function createUser() {
  return {
    id: 1,
    name: "Анна",
  };
}
```

Получим тип самой функции:

```ts
typeof createUser
```

А затем передадим его в `FunctionResult`.

```ts
type CreatedUser = FunctionResult<typeof createUser>;
```

TypeScript посмотрит, что возвращает `createUser`, и извлечёт этот тип.

В результате `CreatedUser` будет примерно таким:

```ts
type CreatedUser = {
  id: number;
  name: string;
};
```

То есть мы не описывали тип пользователя вручную.

Мы получили его из возвращаемого значения функции.

Проверить результат можно, наведя курсор на `CreatedUser` в VS Code.

Теперь посмотрим на ещё один пример.

Допустим, у нас есть `Promise<number>` и мы хотим получить тип значения внутри `Promise`.

Создадим такой тип:

```ts
type PromiseValue<T> =
  T extends Promise<infer TValue>
    ? TValue
    : T;
```

Читается он так:

> «Если `T` является `Promise`, извлеки тип значения внутри него и назови этот тип `TValue`.»

Используем его.

```ts
type AsyncNumber = PromiseValue<Promise<number>>;
```

TypeScript сопоставляет:

```ts
Promise<number>
```

с шаблоном:

```ts
Promise<infer TValue>
```

И понимает, что `TValue` — это `number`.

Поэтому результат будет таким:

```ts
type AsyncNumber = number;
```

Если передать обычный тип, а не `Promise`, сработает вторая ветка.

```ts
type RegularString = PromiseValue<string>;
```

Результатом будет:

```ts
type RegularString = string;
```

Итак, `infer` используется внутри условного типа и позволяет извлечь нужную часть сложного типа.

Это может быть возвращаемый тип функции, элемент массива, значение `Promise` или другая часть известной структуры.

При этом для работы с асинхронными значениями в TypeScript уже существует встроенный тип `Awaited`.

Он обрабатывает не только обычные, но и вложенные `Promise`.

Например:

```ts
type Result = Awaited<Promise<Promise<number>>>;
```

Результатом будет:

```ts
type Result = number;
```

Поэтому на практике для извлечения значения из `Promise` обычно лучше использовать `Awaited`.

А собственный `PromiseValue` здесь нужен прежде всего для того, чтобы понять принцип работы `infer`.

## 7. Mapped types

Теперь разберём mapped types, или отображаемые типы.

Они позволяют взять существующий тип, пройти по всем его свойствам и создать на их основе новый тип.

Возьмём знакомый `User`.

```ts
type User = {
  id: number;
  name: string;
  active: boolean;
};
```

Допустим, нам нужен новый тип с теми же ключами, но все значения должны быть `boolean`.

Напишем:

```ts
type Flags<T> = {
  [K in keyof T]: boolean;
};
```

Разберём эту запись.

```ts
keyof T
```

получает все ключи типа `T`.

А конструкция:

```ts
K in keyof T
```

означает:

> «Пройди по каждому ключу типа `T`.»

Для каждого найденного ключа мы создаём свойство с типом `boolean`.

Теперь применим этот тип к `User`.

```ts
type UserFlags = Flags<User>;
```

TypeScript возьмёт ключи:

```ts
"id" | "name" | "active"
```

и создаст новый тип:

```ts
type UserFlags = {
  id: boolean;
  name: boolean;
  active: boolean;
};
```

То есть mapped type сохраняет ключи, но позволяет изменить тип их значений.

Теперь сделаем все свойства необязательными.

```ts
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};
```

Здесь мы снова проходим по всем ключам.

Но теперь после имени свойства добавлен знак вопроса:

```ts
[K in keyof T]?
```

Это делает каждое свойство необязательным.

А запись:

```ts
T[K]
```

получает исходный тип свойства.

Если применить `MyPartial` к `User`:

```ts
type PartialUser = MyPartial<User>;
```

получится:

```ts
type PartialUser = {
  id?: number;
  name?: string;
  active?: boolean;
};
```

Именно по такому принципу работает встроенный тип `Partial<T>`.

Теперь сделаем свойства только для чтения.

```ts
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};
```

К каждому свойству добавляется модификатор `readonly`.

В результате:

```ts
type ReadonlyUser = MyReadonly<User>;
```

получит такой вид:

```ts
type ReadonlyUser = {
  readonly id: number;
  readonly name: string;
  readonly active: boolean;
};
```

Так работает встроенный тип `Readonly<T>`.

Mapped types позволяют не только добавлять модификаторы, но и снимать их.

Например, уберём `readonly`.

```ts
type Mutable<T> = {
  -readonly [K in keyof T]: T[K];
};
```

Минус перед `readonly` означает:

> «Убери модификатор `readonly` у каждого свойства.»

Допустим, у нас есть такой тип:

```ts
type ReadonlyUser = {
  readonly id: number;
  readonly name: string;
};
```

Применим `Mutable`.

```ts
type EditableUser = Mutable<ReadonlyUser>;
```

Получится:

```ts
type EditableUser = {
  id: number;
  name: string;
};
```

Теперь свойства снова можно изменять.

Аналогично можно убрать необязательность.

```ts
type RequiredFields<T> = {
  [K in keyof T]-?: T[K];
};
```

Минус перед знаком вопроса:

```ts
-?
```

означает:

> «Убери необязательность у каждого свойства.»

Например:

```ts
type OptionalUser = {
  id?: number;
  name?: string;
};
```

Применим наш тип.

```ts
type RequiredUser = RequiredFields<OptionalUser>;
```

Результат:

```ts
type RequiredUser = {
  id: number;
  name: string;
};
```

Итак, mapped types позволяют пройти по ключам существующего типа и создать новый тип.

При этом мы можем:

* заменить типы значений;
* сделать свойства необязательными;
* добавить `readonly`;
* убрать `readonly`;
* убрать необязательность.

Главная конструкция здесь выглядит так:

```ts
[K in keyof T]
```

Она означает:

> «Создай свойство для каждого ключа типа `T`.»

## 8. Переименование ключей

Mapped types позволяют не только проходить по существующим свойствам, но и создавать для них новые имена.

Рассмотрим пример с событиями.

```ts
type Events = {
  userCreated: {
    userId: number;
  };

  orderPaid: {
    orderId: number;
    amount: number;
  };
};
```

Здесь ключи — это названия событий.

А значения — данные, которые передаются вместе с событием.

Теперь допустим, что на основе этого типа мы хотим автоматически создать обработчики:

```ts
onUserCreated
onOrderPaid
```

Для этого напишем mapped type.

```ts
type EventHandlers<T> = {
  [K in keyof T as `on${Capitalize<string & K>}`]:
    (payload: T[K]) => void;
};
```

Разберём эту запись по частям.

Сначала уже знакомая конструкция:

```ts
K in keyof T
```

Она означает:

> «Пройди по каждому ключу типа `T`.»

Для типа `Events` это будут ключи:

```ts
"userCreated" | "orderPaid"
```

Но теперь после `keyof T` появляется ключевое слово `as`.

```ts
K in keyof T as ...
```

Здесь `as` используется не как утверждение типа.

Оно означает:

> «Создай для текущего свойства новое имя.»

Новое имя строится с помощью шаблонного строкового типа:

```ts
`on${Capitalize<string & K>}`
```

Сначала к имени добавляется приставка `on`.

Затем встроенный тип `Capitalize` делает первую букву заглавной.

Например, ключ:

```ts
"userCreated"
```

превращается в:

```ts
"onUserCreated"
```

А ключ:

```ts
"orderPaid"
```

превращается в:

```ts
"onOrderPaid"
```

Теперь посмотрим на тип значения:

```ts
(payload: T[K]) => void
```

Для каждого события создаётся функция.

Параметр этой функции получает тип соответствующего события.

Применим mapped type:

```ts
type Handlers = EventHandlers<Events>;
```

В результате получится тип, эквивалентный следующему:

```ts
type HandlersEquivalent = {
  onUserCreated(
    payload: {
      userId: number;
    },
  ): void;

  onOrderPaid(
    payload: {
      orderId: number;
      amount: number;
    },
  ): void;
};
```

То есть TypeScript автоматически:

* прошёл по событиям;
* переименовал их;
* добавил приставку `on`;
* сделал первую букву заглавной;
* создал правильный тип параметра для каждого обработчика.

Теперь отдельно разберём запись:

```ts
string & K
```

Оператор `keyof` может возвращать не только строки, но также числа и символы.

А шаблонные строковые типы работают со строковыми представлениями.

Поэтому запись:

```ts
string & K
```

оставляет только строковую часть ключа.

Для этого урока достаточно воспринимать её так:

> «Используй `K` как строковый ключ.»

Теперь посмотрим на ещё одну возможность.

При переименовании ключей можно не только менять их имена, но и полностью удалять некоторые свойства.

Для этого используется `never`.

Допустим, мы хотим получить из типа только строковые свойства.

```ts
type StringProperties<T> = {
  [K in keyof T as T[K] extends string ? K : never]:
    T[K];
};
```

Возьмём тип `User`.

```ts
type User = {
  id: number;
  name: string;
  active: boolean;
};
```

Mapped type снова проходит по всем ключам.

Для каждого свойства проверяется условие:

```ts
T[K] extends string
```

Если тип свойства является строкой, ключ сохраняется:

```ts
? K
```

Если нет, вместо ключа возвращается:

```ts
: never
```

А ключ, который превратился в `never`, не попадает в итоговый тип.

Применим преобразование:

```ts
type UserStrings = StringProperties<User>;
```

Свойство `id` имеет тип `number`, поэтому оно удаляется.

Свойство `active` имеет тип `boolean`, поэтому оно тоже удаляется.

Свойство `name` имеет тип `string`, поэтому оно остаётся.

Результат:

```ts
type UserStrings = {
  name: string;
};
```

Итак, конструкция `as` внутри mapped type позволяет управлять ключами.

С её помощью можно:

* переименовывать свойства;
* создавать имена по шаблону;
* добавлять приставки;
* изменять регистр;
* удалять ненужные ключи через `never`.

## 9. Template literal types

До этого момента мы строили новые типы из существующих.

Но TypeScript умеет создавать даже новые строковые типы.

Для этого используются **template literal types**.

По синтаксису они очень похожи на шаблонные строки JavaScript.

Посмотрим на пример.

```ts
type Resource = "user" | "order";

type Action =
  | "create"
  | "update"
  | "delete";
```

Есть два объединения строковых литералов.

Теперь объединим их.

```ts
type Permission =
  `${Resource}:${Action}`;
```

Эта запись читается так:

> «Подставь вместо `Resource` каждое возможное значение и вместо `Action` тоже каждое возможное значение.»

TypeScript автоматически перебирает все комбинации.

В результате получится такой тип:

```text
"user:create"
"user:update"
"user:delete"
"order:create"
"order:update"
"order:delete"
```

То есть из двух небольших объединений автоматически получилось шесть различных строк.

Это очень удобно.

Если позже мы добавим ещё одно действие:

```ts
type Action =
  | "create"
  | "update"
  | "delete"
  | "read";
```

То все новые варианты будут созданы автоматически.

Ничего перечислять вручную уже не потребуется.

Теперь посмотрим, где это действительно используется.

Например, при описании маршрутов приложения.

Пусть идентификатор товара может быть строкой или числом.

```ts
type EntityId = string | number;
```

Теперь опишем маршрут.

```ts
type DetailRoute =
  `/products/${EntityId}`;
```

Этот тип означает:

> «Любая строка должна начинаться с `/products/`, а дальше должен идти идентификатор.»

Проверим.

```ts
const route: DetailRoute =
  "/products/42";
```

Такой маршрут подходит.

Подойдёт и такой:

```ts
const route: DetailRoute =
  "/products/abc";
```

А вот такой уже вызовет ошибку.

```ts
const route: DetailRoute =
  "/users/42";
```

Потому что строка не соответствует заданному шаблону.

Важно понимать, что здесь проверяется именно форма строки.

TypeScript убеждается, что литерал соответствует нужному шаблону.

Но если строка приходит во время выполнения программы, например из браузера, адресной строки или запроса к серверу, никакой проверки автоматически не происходит.

Например:

```ts
const route = window.location.pathname;
```

Тип такой переменной будет просто `string`.

TypeScript не может заранее узнать её содержимое.

Поэтому template literal types проверяют только типы на этапе компиляции, а не реальные данные во время выполнения программы.

Итак, template literal types позволяют строить новые строковые литеральные типы по шаблону.

Они особенно полезны для описания маршрутов, разрешений, имён событий, ключей конфигурации и других строк, которые должны иметь строго определённую форму.

## 10. Рекурсивные типы

До этого момента мы создавали типы, которые преобразовывали существующие типы только один раз.

Но иногда этого недостаточно.

Иногда тип должен уметь обращаться сам к себе.

Такие типы называются **рекурсивными**.

Самый известный пример — описание JSON.

Сначала опишем простые значения.

```ts
type JsonPrimitive =
  | string
  | number
  | boolean
  | null;
```

Теперь создадим основной тип.

```ts
type JsonValue =
  | JsonPrimitive
  | JsonValue[]
  | {
      [key: string]: JsonValue;
    };
```

На первый взгляд запись выглядит необычно.

Но давайте разберём её.

JSON может быть простым значением.

Например:

```json
42
```

или

```json
"hello"
```

Поэтому первая часть — это `JsonPrimitive`.

Но JSON может быть и массивом.

Например:

```json
[1, 2, 3]
```

или

```json
["A", "B"]
```

Поэтому появляется:

```ts
JsonValue[]
```

Обратите внимание.

Элемент массива снова имеет тип `JsonValue`.

То есть массив может содержать всё тот же JSON.

Наконец, JSON может быть объектом.

Например:

```json
{
  "name": "Анна",
  "age": 25
}
```

И значения его свойств снова могут быть любым JSON.

Поэтому внутри объекта снова используется:

```ts
JsonValue
```

Получается, тип ссылается сам на себя.

Именно поэтому он называется рекурсивным.

Теперь рассмотрим ещё один пример.

Допустим, мы хотим сделать объект полностью неизменяемым.

Не только верхний уровень.

Но и все вложенные объекты.

И даже массивы.

Для этого можно написать тип:

```ts
type DeepReadonly<T> =
  T extends (...args: never[]) => unknown
    ? T
    : T extends readonly unknown[]
      ? {
          readonly [K in keyof T]:
            DeepReadonly<T[K]>;
        }
      : T extends object
        ? {
            readonly [K in keyof T]:
              DeepReadonly<T[K]>;
          }
        : T;
```

Не пугайтесь этой записи.

Нас сейчас интересует только общая идея.

Создадим обычный тип.

```ts
type Settings = {
  user: {
    name: string;
    roles: string[];
  };
};
```

Теперь применим `DeepReadonly`.

```ts
type FrozenSettings =
  DeepReadonly<Settings>;
```

Что произойдёт?

Сначала TypeScript сделает `readonly` для свойств объекта.

Затем увидит, что внутри находится ещё один объект.

И снова применит `DeepReadonly`.

Потом обнаружит массив.

И снова применит `DeepReadonly`.

Так происходит до тех пор, пока не останутся только простые значения.

В результате получится тип, в котором нельзя изменить ничего.

Нельзя изменить пользователя.

Нельзя изменить имя.

Нельзя изменить даже элементы массива `roles`.

Именно поэтому такой тип называется **глубоким readonly**.

Главная идея рекурсивных типов очень проста.

Тип может использовать самого себя для обработки вложенных структур.

Но здесь важно соблюдать осторожность.

Рекурсивные типы довольно быстро становятся сложными.

Ошибки компилятора могут получаться очень длинными.

Кроме того, не существует универсального типа, который одинаково хорошо работает для всех случаев.

Например, объекты `Date`, `Map`, `Set`, экземпляры классов и функции требуют отдельной обработки.

Поэтому на практике рекурсивные типы обычно создают для решения конкретной задачи, а не пытаются написать один «идеальный» универсальный тип для всего.

## 11. Типизированная система событий

В этом уроке мы познакомились с разными инструментами вычисления типов.

Теперь посмотрим, как они объединяются в реальном примере.

Представим, что в приложении происходят различные события.

Например, создаётся пользователь или оплачивается заказ.

Опишем их.

```ts
type AppEvents = {
  "user:created": {
    userId: number;
    name: string;
  };

  "order:paid": {
    orderId: number;
    amount: number;
  };
};
```

Здесь ключи — это названия событий.

А значения — данные, которые передаются вместе с каждым событием.

Теперь получим все возможные имена событий.

```ts
type EventName = keyof AppEvents;
```

Мы уже знаем, что делает `keyof`.

Поэтому результат будет таким:

```ts
"user:created" | "order:paid"
```

Теперь создадим тип одного события.

```ts
type EventEnvelope<K extends EventName> = {
  type: K;
  payload: AppEvents[K];
  timestamp: Date;
};
```

Разберём его.

Поле `type` хранит название события.

Поле `timestamp` содержит время возникновения события.

А самое интересное находится здесь:

```ts
payload: AppEvents[K];
```

Мы уже встречали такую запись.

Это Indexed Access Type.

Она означает:

> «Возьми тип свойства `K` из объекта `AppEvents`.»

Например, если `K` равно:

```ts
"user:created"
```

то получится такой тип:

```ts
type UserCreatedEvent = {
  type: "user:created";
  payload: {
    userId: number;
    name: string;
  };
  timestamp: Date;
};
```

А если `K` равно:

```ts
"order:paid"
```

то `payload` автоматически станет:

```ts
{
  orderId: number;
  amount: number;
}
```

То есть для каждого события TypeScript сам подставляет правильный тип данных.

Но обычно приложение работает не с одним конкретным событием, а с любым возможным.

Для этого создадим объединение всех событий.

```ts
type AnyEvent = {
  [K in EventName]: EventEnvelope<K>;
}[EventName];
```

На первый взгляд запись кажется сложной.

Но если разобрать её по шагам, всё становится понятнее.

Сначала работает mapped type.

Он проходит по каждому имени события и создаёт новый объект.

Получается примерно вот это:

```ts
{
  "user:created":
    EventEnvelope<"user:created">;

  "order:paid":
    EventEnvelope<"order:paid">;
}
```

Это обычный объект типов.

Теперь используется Indexed Access Type.

```ts
[EventName]
```

Мы уже знаем, что такая запись получает тип свойства.

Но здесь ключей несколько.

Поэтому TypeScript берёт значения всех свойств сразу.

В результате получается объединение:

```ts
EventEnvelope<"user:created">
|
EventEnvelope<"order:paid">
```

Именно это объединение и хранится в типе `AnyEvent`.

Теперь можно написать функцию обработки событий.

```ts
function handleEvent(
  event: AnyEvent,
): void {
  switch (event.type) {
    case "user:created":
      console.log(event.payload.name);
      break;

    case "order:paid":
      console.log(event.payload.amount);
      break;
  }
}
```

Посмотрите, что здесь происходит.

Внутри `switch` TypeScript анализирует значение поля `type`.

Если это:

```ts
"user:created"
```

то компилятор автоматически понимает, что `payload` имеет тип:

```ts
{
  userId: number;
  name: string;
}
```

Поэтому можно спокойно обращаться к свойству:

```ts
event.payload.name
```

Во второй ветке происходит то же самое.

Если тип события:

```ts
"order:paid"
```

то `payload` автоматически становится:

```ts
{
  orderId: number;
  amount: number;
}
```

И появляется доступ к полю:

```ts
event.payload.amount
```

Без каких-либо дополнительных проверок или приведения типов.

Именно в этом и заключается сила TypeScript.

Используя уже знакомые нам инструменты — `keyof`, Indexed Access Types, mapped types и объединения — можно построить полностью типизированную систему событий, в которой каждому событию автоматически соответствует свой собственный тип данных, а компилятор сам контролирует правильность их использования.

Для завершения урока можно сделать краткий итог: вычисляемые типы не создают новые возможности во время выполнения программы, а помогают автоматически строить и поддерживать сложные типы на этапе компиляции.
