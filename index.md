# Урок 8. Сужение типов и исчерпывающая обработка

Объединение сообщает: значение может иметь несколько форм. Сужение отвечает: как доказать, какая форма находится перед нами в конкретной ветви программы.


---

# 1. typeof

В предыдущем уроке мы познакомились с объединением типов.

Например, переменная может быть либо строкой, либо числом.

```ts
function normalizeId(id: string | number): string {
```

Для TypeScript это означает:

> «Я знаю, что здесь либо `string`, либо `number`, но пока не знаю, что именно.»

Возникает проблема.

У строк есть метод `trim()`.

У чисел его нет.

Если сразу написать:

```ts
id.trim();
```

TypeScript выдаст ошибку.

Он не может гарантировать, что перед ним действительно строка.

Поэтому сначала нужно доказать компилятору, какой тип находится в переменной.

Самый простой способ — оператор `typeof`.

```ts
function normalizeId(id: string | number): string {
  if (typeof id === "number") {
    return id.toString();
  }

  return id.trim().toLowerCase();
}
```

Разберём этот код.

В условии мы спрашиваем:

> Является ли `id` числом?

Если ответ «да», то внутри блока `if` TypeScript уже знает:

> Здесь `id` имеет тип `number`.

Поэтому становятся доступны все методы числа.

Например:

```ts
id.toString();
```

После этого выполняется `return`, и функция завершается.

А что остаётся после `if`?

Мы уже обработали случай, когда `id` — число.

Значит дальше может остаться только строка.

Именно поэтому здесь:

```ts
return id.trim().toLowerCase();
```

TypeScript разрешает вызвать `trim()` и `toLowerCase()`.

Он понимает, что это уже точно строка.

Такое уменьшение количества возможных типов называется **сужением типов**, или **type narrowing**.

В начале функции возможны два варианта:

```text
string | number
```

После проверки остаётся только один:

```text
string
```

Именно это и называется сужением.

---

`typeof` умеет распознавать несколько встроенных типов JavaScript.

На практике чаще всего используются:

* `"string"`
* `"number"`
* `"boolean"`
* `"undefined"`
* `"function"`

Полный список немного длиннее, но запоминать его сейчас необязательно.

Есть одна историческая особенность JavaScript, о которой обязательно нужно знать.

Посмотрите:

```ts
typeof null === "object";
```

Результат будет:

```text
true
```

Хотя `null` объектом не является.

Это старое поведение JavaScript, которое сохранили ради совместимости.

Поэтому, если вы хотите проверить, что значение действительно является объектом, одной проверки `typeof` недостаточно.

Обычно пишут так:

```ts
function isObject(value: unknown): value is object {
  return typeof value === "object" && value !== null;
}
```

Здесь сначала проверяется, что значение имеет тип `"object"`.

А затем отдельно исключается `null`.

Такую запись вы будете регулярно встречать в реальных проектах.

---

Запомните главное правило этого раздела.

**`typeof` нужен не для преобразования типов.**

Он нужен, чтобы **доказать TypeScript**, какой тип находится в переменной в данный момент.

После такой проверки компилятор автоматически сужает тип и разрешает использовать методы, доступные именно этому типу.


Вот как я бы объяснил этот раздел.

# 2. Truthiness narrowing

До этого мы сужали тип с помощью `typeof`.

Но в JavaScript существует ещё один очень распространённый способ проверки.

Посмотрите на пример.

```ts
function printTitle(title: string | null | undefined): void {
  if (title) {
    console.log(title.toUpperCase());
  }
}
```

На первый взгляд кажется, что мы просто проверяем наличие заголовка.

Но на самом деле происходит немного больше.

В JavaScript некоторые значения считаются ложными, даже если это не `false`.

Например:

false
0
""
null
undefined
NaN


Если такое значение попадёт в условие `if`, ветка не выполнится.

Поэтому в нашем примере:

```ts
if (title)
```

TypeScript понимает, что внутри блока `if` переменная уже **не может быть** `null` или `undefined`.

Следовательно, здесь безопасно вызвать:

```ts
title.toUpperCase();
```

Это тоже пример сужения типов.

---

Но есть одна тонкость.

Пустая строка тоже считается ложным значением.

Например:

```ts
printTitle("");
```

Условие

```ts
if (title)
```

не выполнится.

Хотя пустая строка — это всё ещё строка.

Иногда это именно то поведение, которое нам нужно.

Но иногда пустая строка имеет собственный смысл.

Например, пользователь специально очистил поле ввода.

В таком случае лучше выполнять точную проверку.

```ts
function printTitleExactly(
  title: string | null | undefined,
): void {
  if (title === null || title === undefined) {
    console.log("Заголовок не задан");
    return;
  }

  console.log(title.toUpperCase());
}
```

Теперь мы исключаем только два значения:

* `null`;
* `undefined`.

А пустая строка считается корректной строкой и будет обработана.

---

Такая же ситуация возникает с числами.

Предположим, мы пишем:

```ts
if (count) {
  console.log(count);
}
```

Если `count` равен нулю,

```ts
count = 0;
```

условие тоже не выполнится.

Хотя ноль — это вполне корректное число.

Поэтому для чисел лучше писать явные проверки, например:

```ts
if (count !== undefined)
```

или

```ts
if (count !== null)
```

в зависимости от того, какие значения допускает переменная.

---

Запомните простое правило.

Проверка

```ts
if (value)
```

не означает:

> «Есть ли значение?»

Она означает:

> «Является ли значение истинным с точки зрения JavaScript?»

Поэтому такой способ отлично подходит, когда вас устраивают все правила JavaScript.

Если же `0` или пустая строка имеют самостоятельный смысл, лучше выполнять явную проверку `null` и `undefined`.

# 3. Сравнение

Мы уже научились сужать типы с помощью `typeof` и обычных проверок.

Но TypeScript умеет делать это и во время сравнения двух значений.

Посмотрите на пример.

```ts
function compare(
  left: string | number,
  right: string | boolean,
): boolean {
  if (left === right) {
    return left.toLowerCase() === right.toLowerCase();
  }

  return false;
}
```

В начале функции TypeScript знает следующее.

Первая переменная может быть:

```text
string или number
```

Вторая:

```text
string или boolean
```

Теперь посмотрим на условие:

```ts
if (left === right)
```

Что должно произойти, чтобы две переменные оказались равны?

Например, возможен такой вызов:

```ts
compare("Admin", "admin");
```

Обе переменные — строки.

Но если одна переменная — число, а другая — логическое значение,

```ts
compare(10, true);
```

они никогда не будут равны.

То же самое относится к числу и строке:

```ts
compare(10, "10");
```

Строгое сравнение `===` вернет `false`, потому что типы разные.

Поэтому внутри условия

```ts
if (left === right)
```

TypeScript делает простой вывод:

> Если две переменные действительно оказались равны, значит обе они должны быть строками.

Именно поэтому здесь разрешено вызвать:

```ts
left.toLowerCase();
right.toLowerCase();
```

Компилятор уже знает, что обе переменные имеют тип `string`.

Это тоже пример сужения типов.

---

В конце раздела стоит упомянуть ещё одну особенность JavaScript.

Иногда можно встретить такую проверку:

```ts
if (value == null) {
  // ...
}
```

Обратите внимание: здесь используется двойное равенство.

Такая запись одновременно проверяет два случая:

* `value === null`;
* `value === undefined`.

То есть фактически она означает:

```ts
if (value === null || value === undefined) {
  // ...
}
```

Это известная особенность JavaScript.

Однако в учебном курсе мы будем использовать строгие сравнения:

```ts
value === null
value === undefined
```

Они читаются понятнее и не вызывают вопросов, особенно если вы только начинаете изучать TypeScript.


Я бы объяснил это так.

# 4. Оператор in

До этого мы определяли тип по значению.

Например, с помощью `typeof`.

Но иногда два объекта имеют одинаковый тип `"object"`.

Как тогда понять, какой из них перед нами?

Посмотрите на пример.

```ts id="1whw0m"
type Cat = {
  meow(): void;
};

type Dog = {
  bark(): void;
};
```

У кошки есть метод `meow()`.

У собаки — метод `bark()`.

Теперь напишем функцию.

```ts id="b0gkql"
function makeSound(animal: Cat | Dog): void {
  if ("meow" in animal) {
    animal.meow();
  } else {
    animal.bark();
  }
}
```

Параметр `animal` может быть либо кошкой, либо собакой.

Поэтому сразу написать

```ts id="lxb95x"
animal.meow();
```

нельзя.

Вдруг перед нами собака?

В этом случае TypeScript выдаст ошибку.

Поэтому сначала выполняется проверка:

```ts id="7e2t04"
"meow" in animal
```

Она читается так:

> Есть ли у объекта свойство `meow`?

Если ответ «да», TypeScript делает вывод:

> Значит перед нами кошка.

Поэтому внутри `if` переменная автоматически получает тип `Cat`.

В ветке `else` остаётся единственный вариант — `Dog`.

Именно поэтому здесь без ошибок вызывается:

```ts id="r5x3bo"
animal.bark();
```

Это ещё один способ сужения типов.

---

Однако есть одна особенность.

Представьте такой тип.

```ts id="1vqjmk"
type Human = {
  meow?: () => void;
  bark?: () => void;
};
```

Обратите внимание на знак вопроса.

Оба свойства необязательны.

Это означает, что объект может содержать:

* только `meow`;
* только `bark`;
* оба метода;
* ни одного метода.

В этом случае проверка

```ts id="jlwm2d"
"meow" in animal
```

уже не гарантирует, что перед нами именно нужный объект.

Кроме того, наличие свойства ещё не означает, что в нём действительно находится функция.

Например:

```ts id="8ch4vp"
const obj = {
  meow: 123,
};
```

Свойство `meow` существует.

Проверка

```ts id="es0tpb"
"meow" in obj
```

вернёт `true`.

Но вызвать

```ts id="pqxd7w"
obj.meow();
```

невозможно.

Поэтому при работе с неизвестными данными обычно выполняют ещё одну проверку.

```ts id="jk6y9f"
if ("meow" in obj && typeof obj.meow === "function") {
  obj.meow();
}
```

Здесь мы убеждаемся не только в наличии свойства, но и в том, что это действительно функция.

---

Запомните простое правило.

Оператор

```ts id="hffcr4"
in
```

используется, чтобы проверить, **есть ли у объекта определённое свойство**.

После такой проверки TypeScript может автоматически определить, с каким вариантом объекта вы сейчас работаете.

Вот так я бы объяснил этот раздел.

# 5. `instanceof`

До этого мы определяли тип с помощью `typeof` или проверяли наличие свойства через оператор `in`.

Но иногда этого недостаточно.

Например, объект может быть экземпляром какого-то класса.

Посмотрите на пример.

```ts
function formatError(error: Error | string): string {
  if (error instanceof Error) {
    return `${error.name}: ${error.message}`;
  }

  return error;
}
```

Параметр `error` может быть:

* обычной строкой;
* объектом класса `Error`.

Если сразу написать

```ts
error.message
```

TypeScript выдаст ошибку.

Ведь строка не имеет свойства `message`.

Поэтому сначала выполняется проверка:

```ts
error instanceof Error
```

Она читается так:

> «Является ли объект экземпляром класса `Error`?»

Если ответ «да», TypeScript понимает:

> Теперь `error` точно имеет тип `Error`.

Именно поэтому внутри `if` можно спокойно обращаться к свойствам:

```ts
error.name
error.message
```

Если же проверка не прошла, остаётся второй вариант — обычная строка.

Поэтому в конце функции мы просто возвращаем её.

---

Где ещё используется `instanceof`?

Например, с классом `Date`.

```ts
const value: Date | string = new Date();

if (value instanceof Date) {
  console.log(value.getFullYear());
}
```

После проверки TypeScript знает, что `value` — объект `Date`, и разрешает вызвать метод `getFullYear()`.

---

Важно понимать, что `instanceof` работает **только с классами**.

Например:

* `Date`;
* `Error`;
* ваши собственные классы.

А вот с интерфейсами так сделать нельзя.

```ts
interface User {
  name: string;
}
```

Нельзя написать:

```ts
value instanceof User;
```

Почему?

Потому что интерфейс существует **только во время компиляции TypeScript**.

Когда программа превращается в JavaScript, интерфейс полностью исчезает.

В результате во время выполнения никакого `User` уже не существует, а значит проверять просто нечего.

---

Запомните простое правило.

* **`typeof`** — используется для примитивов (`string`, `number`, `boolean` и т.д.).
* **`in`** — проверяет наличие свойства у объекта.
* **`instanceof`** — проверяет, является ли объект экземпляром определённого класса.

Именно поэтому `instanceof` подходит для `Date`, `Error` и собственных классов, но никогда не используется с интерфейсами.

Этот раздел я бы упростил. Главное здесь — показать, что TypeScript анализирует **ход выполнения программы**, а не только отдельные проверки.

# 6. Анализ присваиваний и ранних выходов

До этого мы сужали типы с помощью условий.

Но TypeScript анализирует не только сами условия, а всю логику программы.

Посмотрите на пример.

```ts
function getLength(value: string | string[]): number {
  if (typeof value === "string") {
    return value.length;
  }

  return value.length;
}
```

В начале функции `value` может быть:

```text
string | string[]
```

Дальше выполняется проверка.

Если `value` — строка, функция сразу завершается:

```ts
return value.length;
```

После этого TypeScript делает простой вывод:

> Если программа дошла до следующей строки, значит `value` уже не строка.

Следовательно, здесь:

```ts
return value.length;
```

переменная имеет тип

```text
string[]
```

Это произошло без дополнительной проверки.

TypeScript просто проанализировал поток выполнения программы.

---

То же самое происходит после присваивания.

Посмотрите на пример.

```ts
let value: string | number =
  Math.random() > 0.5 ? "42" : 42;

if (typeof value === "string") {
  value = Number(value);
}

console.log(value.toFixed(2));
```

Сначала `value` может быть либо строкой, либо числом.

Если это строка, мы преобразуем её в число:

```ts
value = Number(value);
```

Если это уже число, ничего не происходит.

Получается, после `if` возможны два варианта:

* было число;
* была строка, но мы превратили её в число.

В обоих случаях результат один.

Поэтому здесь:

```ts
value.toFixed(2);
```

TypeScript знает, что `value` — это число.

---

Но обратите внимание на важную деталь.

Это не означает, что переменная навсегда стала числом.

Её объявленный тип по-прежнему такой:

```ts
let value: string | number;
```

Поэтому позже можно снова написать:

```ts
value = "100";
```

и ошибки не будет.

TypeScript различает две вещи:

* **объявленный тип** — тот, который указан при объявлении переменной;
* **текущий вычисленный тип** — тот, который компилятор смог определить в конкретной точке программы.

Именно поэтому после проверки и присваивания переменная может временно считаться числом, хотя её объявленный тип остаётся `string | number`.

---

Запомните главное.

TypeScript анализирует не только проверки `if`, но и весь путь выполнения программы.

Если какая-то ветка завершилась через `return`, или после присваивания значение стало более конкретного типа, компилятор автоматически учитывает это и сужает тип переменной.

Этот раздел я бы построил вокруг одного вопроса:

> **«А что делать, если `typeof`, `in` и `instanceof` уже недостаточно?»**

# 7. Пользовательский type guard

До этого мы использовали встроенные проверки:

* `typeof`;
* `in`;
* `instanceof`.

Но иногда нужно проверить более сложный объект.

Например, пользователя.

```ts
type User = {
  id: number;
  name: string;
};
```

Представьте, что данные пришли из сети.

Их тип — `unknown`.

```ts
const value: unknown = ...
```

Как доказать TypeScript, что это действительно пользователь?

Для этого можно написать собственную функцию проверки.

```ts
function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null;
}
```

Сначала убеждаемся, что перед нами объект.

Затем проверяем его свойства.

```ts
function isUser(value: unknown): value is User {
  return (
    isRecord(value) &&
    typeof value.id === "number" &&
    typeof value.name === "string"
  );
}
```

Обратите внимание на необычный тип результата.

```ts
value is User
```

Он читается так:

> **«Если функция вернула `true`, значит значение имеет тип `User`.»**

Именно это и называется **пользовательским type guard**.

---

Теперь такую функцию можно использовать в обычном условии.

```ts
if (isUser(value)) {
  console.log(value.name);
}
```

После проверки TypeScript автоматически считает, что `value` имеет тип `User`.

Поэтому свойства доступны без каких-либо приведений типов.

---

Очень удобно использовать такие функции вместе с массивами.

Например:

```ts
const values: unknown[] = [
  { id: 1, name: "Анна" },
  null,
  "not user",
];

const users = values.filter(isUser);
```

TypeScript понимает, что после фильтрации останутся только пользователи.

Поэтому тип переменной `users` становится:

```ts
User[]
```

без дополнительных указаний.

---

Но здесь есть важная особенность.

TypeScript **доверяет** функции `isUser`.

Например, можно написать так:

```ts
function isUserLiar(value: unknown): value is User {
  return true;
}
```

Компилятор никаких ошибок не покажет.

Хотя функция вообще ничего не проверяет.

Получается, мы просто обманули TypeScript.

Именно поэтому пользовательские type guard'ы нужно писать внимательно и обязательно проверять в работе программы.

---

Запомните главное.

Пользовательский type guard — это обычная функция, которая возвращает `true` или `false`.

Но если её тип записан как

```ts
value is User
```

то при значении `true` TypeScript начинает считать, что перед ним действительно объект типа `User`. Именно поэтому такие функции позволяют безопасно работать с данными, пришедшими из API, JSON или других внешних источников.

Этот раздел я бы сильно упростил. Новичку важно понять **зачем нужна assertion function**, а не все нюансы синтаксиса.

---

# 8. Assertion function

До этого мы использовали пользовательский type guard.

Он возвращает `true` или `false`.

Например:

```ts
if (isUser(value)) {
  console.log(value.name);
}
```

Но иногда логика программы другая.

Мы не хотим писать `if`.

Мы хотим сказать:

> **«Либо это пользователь, либо программа должна завершиться с ошибкой.»**

Для этого существуют **assertion function**.

Посмотрите на пример.

```ts
function assertIsUser(value: unknown): asserts value is User {
  if (!isUser(value)) {
    throw new Error("Некорректный пользователь");
  }
}
```

Обратите внимание на необычный тип результата.

```ts
asserts value is User
```

Он читается так:

> **«Если функция завершилась без ошибки, значит `value` — это `User`.»**

Теперь используем её.

```ts
const payload: unknown = {
  id: 1,
  name: "Анна",
};

assertIsUser(payload);

console.log(payload.name);
```

После вызова

```ts
assertIsUser(payload);
```

TypeScript уже считает, что `payload` имеет тип `User`.

Поэтому никаких дополнительных проверок больше не требуется.

---

Ещё один очень полезный пример — проверка на `null` и `undefined`.

```ts
function assertDefined<T>(
  value: T,
  message = "Значение отсутствует",
): asserts value is NonNullable<T> {
  if (value === null || value === undefined) {
    throw new Error(message);
  }
}
```

Представьте, что мы ищем пользователя.

```ts
const user = users.find((item) => item.id === 1);
```

Метод `find()` может вернуть объект…

…а может вернуть `undefined`.

Поэтому сразу написать

```ts
user.name;
```

нельзя.

TypeScript выдаст ошибку.

Но если выполнить проверку

```ts
assertDefined(user, "Пользователь не найден");
```

то после неё компилятор знает:

> `user` точно существует.

И поэтому спокойно разрешает написать

```ts
console.log(user.name);
```

---

Запомните различие между двумя видами функций.

**Type guard**

```ts
isUser(value)
```

возвращает `true` или `false`.

Вы сами решаете, что делать дальше.

**Assertion function**

```ts
assertIsUser(value)
```

ничего не возвращает.

Она либо завершается успешно…

…либо сразу выбрасывает исключение.

Поэтому её удобно использовать тогда, когда отсутствие нужного значения считается ошибкой программы.

Например:

* обязательный пользователь;
* обязательная настройка;
* обязательный параметр функции.

В таких ситуациях после одной проверки TypeScript уже считает значение безопасным для дальнейшей работы.

Этот раздел очень важный. Но я бы не начинал со слов **«дискриминируемое объединение»**. Сначала нужно показать проблему.

---

# 9. Дискриминируемое объединение

Представьте, что мы описываем состояние загрузки данных.

Первый вариант может выглядеть так.

```ts
type LooseRequestState<T> = {
  isLoading: boolean;
  data?: T;
  error?: Error;
};
```

На первый взгляд всё выглядит нормально.

Есть флаг загрузки.

Есть данные.

Есть ошибка.

Но такая модель позволяет создать совершенно нелогичное состояние.

```ts
const impossible: LooseRequestState<string[]> = {
  isLoading: true,
  data: ["готово"],
  error: new Error("Ошибка"),
};
```

Получается странная ситуация.

Одновременно:

* данные уже загружены;
* загрузка ещё продолжается;
* и при этом произошла ошибка.

В реальном приложении такого быть не должно.

Но TypeScript не видит здесь ошибки.

Почему?

Потому что свойства никак не связаны друг с другом.

---

Поэтому обычно используют другую модель.

```ts
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };
```

Теперь каждое состояние описывается отдельным объектом.

Если статус

```ts
status: "success"
```

обязательно существуют данные.

Если статус

```ts
status: "error"
```

обязательно существует ошибка.

А если статус

```ts
status: "loading"
```

то нет ни данных, ни ошибки.

Невозможные комбинации больше нельзя создать.

---

Теперь посмотрим на использование.

```ts
function renderUsers(state: RequestState<User[]>): string {
  switch (state.status) {
    case "idle":
      return "Нажмите «Загрузить»";

    case "loading":
      return "Загрузка...";

    case "success":
      return state.data.map((user) => user.name).join(", ");

    case "error":
      return `Ошибка: ${state.error.message}`;
  }
}
```

Обратите внимание на `switch`.

Когда TypeScript видит

```ts
case "success":
```

он сразу понимает:

> Перед нами вариант с успешной загрузкой.

Поэтому здесь без ошибок доступны данные.

```ts
state.data
```

А в ветке

```ts
case "error":
```

доступно только

```ts
state.error
```

Компилятору уже не нужны дополнительные проверки.

Он сам определяет нужный тип по значению поля `status`.

---

Именно поэтому поле

```ts
status
```

называют **дискриминантом**.

Это обычное поле, которое помогает TypeScript понять, с каким вариантом объекта мы сейчас работаем.

---

Запомните главную идею.

Если объект может находиться в нескольких состояниях, лучше описывать каждое состояние отдельным типом и объединять их через `union`.

А специальное поле, например `status`, позволит TypeScript автоматически определить, какие свойства доступны в каждой ветке программы.

Именно такую модель вы будете регулярно встречать в React, Redux Toolkit, TanStack Query и многих других библиотеках.

Этот раздел я бы сделал максимально практичным. Главное — чтобы ученики поняли, **зачем нужен `assertNever`**.

---

# 10. Исчерпывающая проверка

Продолжим работать с нашей моделью состояний.

```ts id="7ln7oi"
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };
```

Мы уже умеем обрабатывать её через `switch`.

Но возникает вопрос.

Что произойдёт, если через месяц кто-нибудь добавит ещё одно состояние?

Например:

```ts id="vg0tvi"
| { status: "refreshing" }
```

Очень легко забыть добавить новый `case`.

Именно для таких ситуаций используют функцию `assertNever`.

```ts id="mxe6sv"
function assertNever(value: never): never {
  throw new Error("Необработанный вариант");
}
```

Теперь посмотрим на `switch`.

```ts id="x2aqkt"
function renderUsersStrict(state: RequestState<User[]>): string {
  switch (state.status) {
    case "idle":
      return "Ожидание";

    case "loading":
      return "Загрузка";

    case "success":
      return `${state.data.length} пользователей`;

    case "error":
      return state.error.message;

    default:
      return assertNever(state);
  }
}
```

Пока обработаны все варианты, ошибок нет.

Почему?

Потому что в ветку `default` программа никогда не должна попасть.

Для TypeScript это означает:

> Здесь значение должно иметь тип `never`.

То есть никаких возможных вариантов больше не осталось.

---

Теперь представим, что кто-то изменил тип.

```ts id="z6b3te"
type RequestState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error }
  | { status: "refreshing" };
```

Но `switch` забыли обновить.

Что происходит?

TypeScript сразу показывает ошибку на строке

```ts id="ofi0eu"
assertNever(state);
```

Почему?

Потому что теперь в `default` может попасть состояние

```ts id="grgjcz"
{ status: "refreshing" }
```

А функция

```ts id="6nqbkq"
assertNever(...)
```

разрешает передавать только тип `never`.

Получается, компилятор сразу сообщает:

> **Вы забыли обработать новый вариант.**

---

Иногда можно обойтись вообще без функции.

Например:

```ts id="d0ufce"
default: {
  state satisfies never;
  return "Недостижимо";
}
```

Здесь происходит только проверка типов.

Если после изменения `RequestState` в `default` останется хотя бы один возможный вариант, TypeScript покажет ошибку.

---

Запомните главное.

`assertNever` нужен не для работы программы во время выполнения.

Он нужен для разработчика.

Если позже в `union` появится новый вариант, а вы забудете добавить новый `case`, компилятор сразу сообщит об этом.

Именно поэтому такой приём называется **исчерпывающей проверкой**: мы гарантируем, что обработали **все** возможные варианты состояния.


### 11. Платёжные операции

Теперь применим дискриминируемое объединение к более жизненному примеру — способам оплаты.

У нас есть три варианта.

Оплата картой:

```ts
type CardPayment = {
  method: "card";
  cardToken: string;
};
```

Оплата по банковскому счёту:

```ts
type BankPayment = {
  method: "bank";
  account: string;
  companyInn: string;
};
```

И оплата через электронный кошелёк:

```ts
type WalletPayment = {
  method: "wallet";
  walletId: string;
};
```

Объединим их в один тип:

```ts
type Payment = CardPayment | BankPayment | WalletPayment;
```

Теперь параметр типа `Payment` может быть одним из трёх вариантов.

Определить конкретный вариант помогает поле:

```ts
method
```

Это дискриминант.

Посмотрим на функцию:

```ts
function describePayment(payment: Payment): string {
  switch (payment.method) {
    case "card":
      return `Карта: ${payment.cardToken.slice(-4)}`;

    case "bank":
      return `Счёт ${payment.account}, ИНН ${payment.companyInn}`;

    case "wallet":
      return `Кошелёк ${payment.walletId}`;

    default:
      return assertNever(payment);
  }
}
```

Когда TypeScript видит:

```ts
case "card":
```

он понимает, что `payment` имеет тип `CardPayment`.

Поэтому здесь доступно свойство:

```ts
payment.cardToken
```

В ветке `"bank"` доступны:

```ts
payment.account
payment.companyInn
```

А в ветке `"wallet"`:

```ts
payment.walletId
```

Главное преимущество такой модели — она не позволяет смешивать поля разных способов оплаты.

Например, такой объект будет ошибочным:

```ts
const payment: Payment = {
  method: "card",
  walletId: "wallet-123",
};
```

TypeScript сообщит, что для оплаты картой требуется `cardToken`, а `walletId` к этому варианту не относится.

Правильный объект выглядит так:

```ts
const payment: Payment = {
  method: "card",
  cardToken: "token-12345678",
};
```

То есть поле `method` определяет, какие остальные поля должны присутствовать в объекте.

А `assertNever` в `default` дополнительно проверяет, что функция обработала все возможные способы оплаты.
